## 2. Chat tab

### bmo chat agent confirms real-world actions that actually failed

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** chat tab → "set an alarm for 7am" and "turn the lights blue" (browser socket.io path + `POST /api/chat`)

**Description:** The assistant's reply text reports success for commands that did not actually run. Two reproduced cases, both via the real dashboard chat (socket.io) and confirmed against `POST /api/chat`:
- "set an alarm for 7am" → reply **"I have set your alarm for 7:00 AM!"**, but `commands_executed` = `[{action: alarm_set, error: "'datetime.timezone' object has no attribute 'key'", success: false}]`, and the alarms list (`/api/timers`) stays **empty** — no alarm exists.
- "turn the lights blue" → reply **"I have set the LED lights to blue for you."**, but `commands_executed` = `[{action: led_set_color, result: "LED controller not available", success: true}]` — the LED controller was never reached (note `success:true` despite an error string result).

So the user is told the action happened when it did not. On a wall-mounted assistant this is a trust/correctness failure (a "set" alarm that never fires).

**Reproduction:**
1. Chat tab → send "set an alarm for 7am" → reply claims success.
2. Open Timers tab (or `GET /api/timers`) → no alarm present.
3. Chat tab → send "turn the lights blue" → reply claims success; LED is unchanged via the chat path.

**Expected behavior:** The reply text must reflect the actual command result — surface a failure ("I couldn't set that alarm") when `success` is false or the tool returned an error string, and the `success` flag must be derived from the tool outcome (an error string is not success).

**Hypothesis / root cause:** The user-facing confirmation text is generated optimistically and is not reconciled against `commands_executed`; additionally the success flag for LED is computed from a truthy return value (the error *string* "LED controller not available" is truthy) rather than an explicit ok/err. See `bmo/pi/agent.py` command-execution + response assembly, and the LED handlers at `agent.py:1520-1551`.

**Suggested action:** Gate the confirmation phrasing on per-command success; map tool returns to explicit `{ok, message}` so error strings can't be reported as `success:true`.

**Environment:** LAN/loopback · online · kiosk off · LED hardware ready (dashboard path), camera/calendar degraded

**Related files:** `bmo/pi/agent.py` (response assembly + `_handle_led_*`), `bmo/pi/services/timer_service.py`

**Console output (if any):** command result error: `'datetime.timezone' object has no attribute 'key'`

**Screenshot(s):** `screenshots/chat-alarm-reply.png`

### Setting an alarm via the chat agent always fails — `'datetime.timezone' object has no attribute 'key'`

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** chat tab → "set an alarm for 7am" (with and without `client_timezone`)

**Description:** Every chat-initiated alarm fails inside `TimerService.create_alarm`. The fallback line builds the timezone name as `datetime.datetime.now().astimezone().tzinfo.key`, but the local `tzinfo` resolved this way is a fixed-offset `datetime.timezone` (the Pi's offset), which has **no `.key` attribute** (only `zoneinfo.ZoneInfo` does) — so it raises `AttributeError` before the very next line's `if not tz_name:` safety net can run. Reproduced via the browser chat and via `POST /api/chat` both with `client_timezone:"America/Chicago"` and without it. The dashboard **UI** alarm path (`POST /api/alarms/create`, which passes `_request_client_timezone(default_to_pi=True)`) works correctly — so the defect is specific to the agent/voice path where the timezone falls through to the broken fallback.

**Reproduction:**
1. `curl -s -X POST http://127.0.0.1:5000/api/chat -H 'Content-Type: application/json' -d '{"message":"set an alarm for 7am","speaker":"unknown"}'`
2. Observe `commands_executed[0].error == "'datetime.timezone' object has no attribute 'key'"`, `success:false`.
3. `GET /api/timers` → alarm not created.
4. Contrast: `POST /api/alarms/create {"hour":7,"minute":0}` → alarm created successfully.

**Expected behavior:** `create_alarm` should resolve a valid IANA tz name on the fallback path (or skip straight to `DEFAULT_EXISTING_ALARMS_TZ`) without dereferencing a non-existent `.key`.

**Hypothesis / root cause:** `bmo/pi/services/timer_service.py:283` — `tz_name = _normalize_timezone(timezone_name) or datetime.datetime.now().astimezone().tzinfo.key`. The `.key` access on a `datetime.timezone` throws; the intended `if not tz_name: tz_name = DEFAULT_EXISTING_ALARMS_TZ` guard on the next line is unreachable dead code. Use e.g. `_normalize_timezone(...) or DEFAULT_EXISTING_ALARMS_TZ`, or `getattr(tzinfo, "key", None)`.

**Suggested action:** Replace the `.key` fallback with a safe IANA resolution (or the existing default constant); add a unit test for `create_alarm` with `timezone_name=None`.

**Environment:** LAN/loopback · online · kiosk off

**Related files:** `bmo/pi/services/timer_service.py:283`, `bmo/pi/agent.py:1709` (`_handle_alarm_set`), `bmo/pi/app.py:851` (REST chat passes `_pi_timezone()`)

**Console output (if any):** `'datetime.timezone' object has no attribute 'key'`

**Screenshot(s):** `screenshots/chat-alarm-reply.png`

### Chat-driven LED control never reaches the controller — service-map key mismatch

- **Category:** bug
- **Severity:** medium
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** chat tab → "turn the lights blue"

**Description:** Every chat LED command returns "LED controller not available", even though the dashboard's own LED panel works (`GET /api/led/status` → `{ok:true, state:"ready", mode:"breathing"}`, and a `mode`/`color` round-trip via `/api/led/*` succeeds). The agent's LED handlers look up `self.services.get("led_controller")`, but `app.py` registers the controller in the service map under the key **`leds`** (`service_map["leds"] = led_controller`). The lookup misses → `None` → "LED controller not available" → then reported to the user as success (see the misreport finding above).

**Reproduction:**
1. Chat → "turn the lights blue" → `commands_executed[0].result == "LED controller not available"`.
2. `GET /api/led/status` → controller is `ready`; `POST /api/led/mode {"mode":"rainbow"}` round-trips fine.

**Expected behavior:** Chat LED commands should drive the same controller the dashboard uses.

**Hypothesis / root cause:** Key mismatch — registered as `service_map["leds"]` (`bmo/pi/app.py:589,599`) but consumed as `services.get("led_controller")` (`bmo/pi/agent.py:1520,1535,1543,1551`). Align the key (register `service_map["led_controller"]` or change the agent lookups to `"leds"`).

**Suggested action:** Use one consistent service key for the LED controller across `app.py` and `agent.py`; add a smoke test that the agent's smart-home LED tool can fetch the controller.

**Environment:** LAN/loopback · online · LED hardware ready

**Related files:** `bmo/pi/app.py:589,599` (registration), `bmo/pi/agent.py:1520-1551` (`_handle_led_*`)

**Screenshot(s):** `screenshots/chat-alarm-reply.png`

## 7. Timers & alarms tab

### Alarm create vs. list show a different local time for the same instant (Pi system-TZ vs configured location-TZ)

- **Category:** UX
- **Severity:** low
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** timers/alarms → `POST /api/alarms/create` then `GET /api/timers`

**Description:** Creating an alarm "for 7:00 AM" with no explicit client timezone returns `target_time:"07:00 AM"` (target_time_utc `13:00:00Z`) in the create response, but the list endpoint formats that **same** UTC instant as `"08:00 AM"`. Root cause: the Pi **system** timezone is `America/Denver` (MDT, −06:00) while the configured **location** is `America/Chicago` (Overland Park, KS; CDT, −05:00) — `13:00Z` is 07:00 Mountain (used to build the alarm) but 08:00 Central (used to display the list). When an explicit `client_timezone` is supplied (as the real dashboard chat does), the alarm anchors correctly (`12:00Z` = 07:00 AM CDT). This Pi-system-TZ vs location-TZ reconciliation is **intentional per `DESIGN-CONSTRAINTS.md`** (header-clock note: "reconciliation remains an owner/config decision — out of scope"); filing only the user-visible inconsistency that the *create* and *list* endpoints format the same instant differently.

**Reproduction:**
1. `POST /api/alarms/create {"hour":7,"minute":0}` (no `client_timezone`) → create says `07:00 AM`, utc `13:00:00Z`.
2. `GET /api/timers` → same alarm shows `08:00 AM`.

**Expected behavior:** Either align both endpoints to format in one canonical tz, or always anchor on the configured location tz, so create and list agree.

**Hypothesis / root cause:** `default_to_pi=True` resolves to the Pi *system* tz (`America/Denver`) for the create, while list formatting uses the configured location tz (`America/Chicago`). Underlying TZ policy is an intentional owner/config decision per DESIGN-CONSTRAINTS; the cross-endpoint formatting mismatch is the actionable nit.

**Suggested action:** Pick one canonical display tz for both create and list responses (likely the configured location tz).

**Environment:** LAN/loopback · Pi system tz America/Denver · location tz America/Chicago

**Related files:** `bmo/pi/app.py` (`_request_client_timezone`, `_pi_timezone`, `/api/alarms/create`, `/api/timers`), `bmo/pi/services/timer_service.py`
