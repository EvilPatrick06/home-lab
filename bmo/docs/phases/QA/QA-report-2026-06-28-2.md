### CRITICAL — the bmo chat agent is 100% non-functional: every message fails with `agent is None`

- **Category:** bug
- **Severity:** critical
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Phase 2 — sending a chat message in the live SPA + REST/socket probes

**Description:** The headline feature is fully down on `655a930f`. Sending "QA probe: what is 2+2?" in the live dashboard returns the error bubble **"Oops! BMO's brain got fuzzy: 'NoneType' object has no attribute 'model_override'"**. Earlier probes in history show "(interrupted — try asking again)" stubs and a wall of canned **"Hello from BMO!"** replies (even to "What time is it?") — i.e. no real model output ever. Both transports fail:
- **REST** `POST /api/chat` -> HTTP 500; server traceback `chat_api.py:59` `result = _app().agent.chat(...)` -> `AttributeError: 'NoneType' object has no attribute 'chat'`.
- **socket.io** chat -> `realtime_ws.py` `prev_model_override = agent.model_override` -> `AttributeError: 'NoneType' object has no attribute 'model_override'` (surfaced to the user as the "brain got fuzzy" bubble).

**Reproduction:**
1. Open the Chat tab, type any message, Send.
2. Observe the "Oops! BMO's brain got fuzzy: 'NoneType' object has no attribute 'model_override'" error bubble.
3. Cross-check REST: `curl -s -X POST http://127.0.0.1:5000/api/chat -H 'Content-Type: application/json' -d '{"message":"hi"}'` -> 500; `sudo journalctl -u bmo.service` shows the `'NoneType' object has no attribute 'chat'` traceback at `chat_api.py:59`.

**Expected behavior:** A real streamed agent response.

**Hypothesis / root cause:** Dual-module bug. The service runs `python app.py` (ExecStart in `bmo/pi/systemd/bmo.service`), so the module that runs `init_services()` and sets the module-global `agent` (`app.py:789 agent = BmoAgent(...)`) is `__main__`. The chat routes resolve the agent via `_app()` which does `import app` (`chat_api.py:25-26`; same pattern feeds `realtime_ws.py`), importing a **second, separate** `app` module object whose module-global `agent` was never initialised and stays `None` (`app.py:503 agent = None`). So `_app().agent` is always `None`. The `b8781746` self-heal added on-demand reinit for **calendar** and **music** (`service_init_status`) but **not for the agent**, and even that runs in whichever module called it — it does not bridge `__main__` vs the imported `app`. Same critical as prior report `QA-report-2026-06-28.md`; **still unresolved**.

**Suggested action:** Resolve the agent through a single shared module/singleton instead of `import app` — e.g. have `_app()` return the running `__main__` module (`sys.modules["__main__"]`) when launched as a script, or move `agent` (and the other service singletons) into a dedicated `services`/`state` module that both the entrypoint and the blueprints import, or expose `app.get_agent()` that lazily builds the agent on first use in the importing module. Add an agent entry to the `service_init` self-heal so a `None` agent self-reconstructs.

**Environment:** external SPA (socket.io) + Pi loopback (REST) · connected (green dot) · normal viewport · 2026-06-28 run 2.

**Related files:** `bmo/pi/routes/chat_api.py:25-26,58-59`, `bmo/pi/routes/realtime_ws.py:~222`, `bmo/pi/app.py:503,561,785-789`, `bmo/pi/systemd/bmo.service` (ExecStart `python app.py`).

**Console output:** UI bubble "Oops! BMO's brain got fuzzy: 'NoneType' object has no attribute 'model_override'"; server `AttributeError: 'NoneType' object has no attribute 'chat'` (REST) / `...has no attribute 'model_override'` (socket).

**Log cross-check:** Not in `BMO-ISSUES-LOG.md`; previously reported only in the QA report `QA-report-2026-06-28.md` and **still unresolved** on the live `655a930f`. (Related class: `BMO-RESOLVED-ISSUES.md` notes `app.py` init catches that leave services `None` with no retry — the `b8781746` self-heal covers calendar/music but not the agent.)

### TV pairing against an unreachable/off TV hangs ~30s with no loading indicator before failing

- **Category:** UX
- **Severity:** medium
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Phase 4 — TV tab -> Pair with TV -> enter PIN -> Connect

**Description:** With the TV off, "Pair with TV" POSTs `/api/tv/pair/start` and shows the PIN screen, but the request stays **pending for ~30s**. Entering a PIN and clicking **Connect** POSTs `/api/tv/pair/finish`, which **also hangs pending** with **no spinner / no disabled state / no feedback** on the Connect button — the screen looks frozen. Only after a long delay (and after Cancel POSTs `/api/tv/pair/cancel`) does a faint top toast "Failed to start pairing" appear and the UI resets to the empty state. Recoverable, but the multi-second dead-air with zero affordance reads as a hang.

**Reproduction:**
1. TV off. TV tab -> "Pair with TV".
2. `/api/tv/pair/start` stays pending; PIN screen shows with no loading hint.
3. Type any PIN -> Connect. `/api/tv/pair/finish` hangs pending ~10s+; Connect shows no spinner/disabled state.
4. Eventually a small "Failed to start pairing" toast appears; UI resets.

**Expected behavior:** Connect/Pair should show an immediate loading state (spinner / disabled button), and the pairing call should time out quickly with a clear inline error ("TV unreachable — is it on and on the same network?") rather than hanging.

**Hypothesis / root cause:** `bmo/pi/routes/tv_api.py` `api_tv_pair_start`/`api_tv_pair_finish` call `_tv_cmd("pair_start")` / `_tv_cmd("pair_finish", pin=...)` (lines ~332, ~349) which round-trip to the long-lived TV worker subprocess; when the TV can't be reached the worker command has **no short timeout**, so the HTTP request blocks until something upstream gives up. The dashboard's Connect handler also lacks a pending/disabled UI state (`bmo/pi/web/static/js/bmo.js` TV pairing handler).

**Suggested action:** Add a short timeout to the `_tv_cmd` pairing round-trip (return a 503 "TV unreachable" fast, like the other TV routes already do for unpaired state), and give the Connect/Pair buttons an immediate spinner + disabled state with an inline error on failure.

**Environment:** external SPA · connected · TV hardware off/unreachable · normal viewport · 2026-06-28 run 2.

**Related files:** `bmo/pi/routes/tv_api.py:329-355` (pair_start/pair_finish; cf. `_tv_cmd`/`_adb_connect` timeout at lines ~132-144), `bmo/pi/web/static/js/bmo.js` (TV pairing UI state).

**Console output:** none; toast "Failed to start pairing".

**Design-constraint cross-check:** `bmo/docs/DESIGN-CONSTRAINTS.md` documents that `updateClock()` renders the **configured-location** timezone (seeded from weather/`/api/config`), never browser-local, and that **Pi-system-TZ vs configured-location-TZ reconciliation is an intentional owner/config decision (out of scope)**. The observed offset is exactly that known item (location Overland Park KS = Central vs Pi system = America/Denver MDT). So my "uses client local time" hypothesis is wrong; treat this as **intentional per DESIGN-CONSTRAINTS** — included only as awareness that alarm countdowns (Pi-system tz) and the header clock (location tz) can visibly diverge.

**Suggested action:** Consider rendering the Pi's authoritative time in the header (or reconciling client vs server time) so countdowns and the clock can't visibly diverge for remote clients.

**Environment:** external SPA on off-Pi Windows Chrome (America/Denver) vs Pi America/Denver MDT · 2026-06-28 run 2.

**Related files:** `bmo/pi/web/static/js/bmo.js` (header clock), timers/alarms tz handling.
