### Backend fixes from phases 1–3 are committed but not running (service not restarted after deploy)
- **Category:** config | **Severity:** high | **Domain:** bmo | **Discovered by:** QA Agent | **During:** loopback API smoke + process/mtime cross-check
- **Description:** The deployed clone is at `8c6811d5` and the phase-1/2/3 backend fixes are present in the on-disk source, but the running Flask process (pid 1726) started at **16:06:16**, ~6 min **before** the source updated on disk (16:12:44). Python imported the old modules at start; there is no reloader. So every `/api/*` call currently serves pre-phase code. Concretely confirmed against the prior pass's #1 High:
  - `POST /api/lists/drugstore/items/<id>/check` and `DELETE /api/lists/drugstore/items/<id>` both still **404** by item id — yet `DELETE …/items/<text>` returns **200**. That is exactly the OLD text-matching behavior. Current source `services/list_service.py:79–93` (`_find_item`) matches **id first**, so the live 404 can only be stale code.
  - `/auth/status` and `/auth/url` return **404** on the live server, although `routes/auth_api.py:128` (`auth_status`) defines them — i.e. the new auth routes aren't loaded.
- **Reproduction:** 1) `ssh patrick@bmo`; 2) `ps -o pid,lstart -p $(ss -ltnp | grep :5000 | grep -oE 'pid=[0-9]+' | cut -d= -f2)` → started 16:06:16; 3) `stat -c %y bmo/pi/app.py` → 16:12:44; 4) add a list item, then `check`/`delete` it by id → 404; delete by text → 200.
- **Expected behavior:** After a deploy that updates `bmo/pi/**`, the bmo Flask service is restarted so the running code matches the checked-out SHA. A QA pass "against `8c6811d5`" should be hitting `8c6811d5`'s backend.
- **Hypothesis / root cause:** The deploy/merge step (the resolver/integrator that produced `e0ab71cb`/`8c6811d5` at 16:12–16:14) updates the working tree but does not restart the user systemd unit / `app.py` process. No file-watch reload is enabled for production `app.py`.
- **Suggested action:** Have the deploy step restart the bmo service after pulling (owner step — this agent may not `systemctl restart` per INSTRUCTIONS §6). Then re-run QA to confirm the phase-1/2/3 fixes live. Optionally expose the running code's SHA via `/api/v1/health` so deploy/runtime skew is detectable.
- **Environment:** Pi loopback · backend pid 1726 (16:06) vs source 16:12 · single-user.
- **Related files:** `bmo/pi/app.py`, `bmo/pi/services/list_service.py`, `bmo/pi/routes/auth_api.py`, the deploy/integrator step.

### Static assets are served fresh while the backend is stale (deploy↔restart version skew)
- **Category:** bug | **Severity:** medium (high if a browser is used in this window) | **Domain:** bmo | **Discovered by:** QA Agent | **During:** build-stamp vs process-start cross-check
- **Description:** `/bmo` cache-busts static assets by file mtime, so it currently serves `bmo.js?v=1782339164` (the 16:12:44 phase-3 build) — but the backend is the 16:06 build. Any browser loading the dashboard right now runs the **new** client JS against the **old** API. The phase-1/2/3 client expects contracts the old backend lacks (list id-matching, `/auth/*`, etc.), so the client would misbehave even though both "halves" are individually fine. This skew exists for the whole window between every deploy and the next restart.
- **Expected behavior:** Client JS and backend come from the same SHA; no window where fresh JS talks to stale Python.
- **Hypothesis / root cause:** Same as above — assets are read from disk per request (fresh), Python is in-memory (stale); restart-after-deploy would close the gap.
- **Suggested action:** Restart on deploy (above). This is also why a browser-based QA in this state would produce misleading "bugs."
- **Related files:** `bmo/pi/app.py` (static cache-bust), deploy step.
