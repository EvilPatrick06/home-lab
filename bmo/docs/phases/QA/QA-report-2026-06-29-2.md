## 2. Chat tab

### Chat-driven LED control never reaches the controller, and the silent failure is masked by a false confirmation

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** chat → LED control root-cause (smart_home routing) + source review

**Description:** When a user asks BMO to change the LEDs in chat ("set the lights blue", "breathing mode", etc.), the router sends the request to the `smart_home` agent, whose reply carries a `led_set_*` command block. That block is executed by the main agent's `_execute_command`, but every LED handler resolves the controller with `self.services.get("led_controller")` — a key that is **never registered**. `app.py` registers the live controller only as `service_map["leds"]` (lines 590 and 600); there is no `led_controller` alias anywhere. So `led` is always `None` and each handler returns the string `"LED controller not available"`. Worse, `led_set_color/led_set_mode/led_set_brightness` are **not** in `INFORMATIONAL_ACTIONS` (only `led_get_state` is), so that error string is never appended to the spoken/displayed reply (`agent.py` ~line 823). The user is shown only the LLM's prose, and the `smart_home` system prompt explicitly instructs it to "Confirm what you did" — so BMO cheerfully claims it set the lights while nothing happened. (The Settings-tab LED controls are unaffected: they POST to `/api/led/*`, which uses the global `led_controller` object directly, and returned `ok:true` in testing.)

**Reproduction:**
1. In the Chat tab, send "set the LEDs to blue" (routes to `smart_home`).
2. The reply reads as a success confirmation (e.g. "Done — your lights are blue now").
3. Inspect `commands_executed` in the `/api/chat` payload (or server log `[agent] led_set_color: ...`): the LED command result is `"LED controller not available"`. The physical/sim LED state does not change.

**Expected behavior:** Either the LED command actually reaches the controller, or — if it genuinely can't — the failure is surfaced to the user instead of a false "done."

**Hypothesis / root cause:** Service-key mismatch: handlers use `led_controller`, registry uses `leds`. Cite `bmo/pi/agent.py:1522,1534,1542,1550` (`self.services.get("led_controller")`) vs `bmo/pi/app.py:590,600` (`service_map["leds"] = led_controller`). Compounding: non-informational command errors are dropped from the user-visible text (`bmo/pi/agent.py` ~`INFORMATIONAL_ACTIONS` block, ~line 823), so the error never reaches the user.

**Suggested action:** Make the keys agree — register `service_map["led_controller"]` as well (or change the four handlers to `.get("leds")`, matching `smart_home_agent`'s declared `services=[..., "led_controller"]`). Separately, surface non-informational command failures (or at least LED/TV/alarm control errors) in the reply so the agent can't falsely confirm a failed real-world action.

**Environment:** LAN/loopback `http://127.0.0.1:5000` · kiosk off · connected · `SimLedController` active · viewport 480×900.

**Related files:** `bmo/pi/agent.py` (`_handle_led_set_color/mode/brightness/get_state`, `INFORMATIONAL_ACTIONS`), `bmo/pi/app.py` (`service_map["leds"]`), `bmo/pi/agents/smart_home_agent.py` (`services=["smart_home","tv","led_controller"]`).

**Console output (if any):** server-side `[agent] led_set_color: LED controller not available` (no browser console error — the failure is swallowed).

**Status vs run 1:** Persists. Flagged in `QA-report-2026-06-29.md` (run 1, top findings #1 + #3); the `605e712f → 7a266d22` redeploy did not change `agent.py`/`app.py` LED wiring. **Not present in `docs/logs/BMO-ISSUES-LOG.md` or `DESIGN-CONSTRAINTS.md`.**

## 7. Timers & alarms tab

### `create_alarm` timezone fallback raises `AttributeError: 'datetime.timezone' object has no attribute 'key'`

- **Category:** bug
- **Severity:** medium
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** alarm path root-cause (run-1 finding #2 re-check) + isolated repro

**Description:** `timer_service.create_alarm` computes its anchor zone as `tz_name = _normalize_timezone(timezone_name) or datetime.datetime.now().astimezone().tzinfo.key` (`bmo/pi/services/timer_service.py:283`). `datetime.datetime.now().astimezone().tzinfo` is a fixed-offset `datetime.timezone`, which has **no `.key`** (only `zoneinfo.ZoneInfo` does), so the fallback raises `AttributeError` whenever it is reached — i.e. whenever `_normalize_timezone(timezone_name)` returns `None` (empty string, or a name that fails `ZoneInfo(...)`). Verified in isolation on the Pi: `type(now().astimezone().tzinfo).__name__ == 'timezone'`, `hasattr(..., 'key') == False`, and `_normalize_timezone("")`/bad input returns `None` (`timer_service.py:16-25`).

**Reproduction:**
1. Call `create_alarm(7, 0, "x", timezone_name="")` (or any string that fails `ZoneInfo`).
2. `_normalize_timezone` → `None` → fallback hits `.tzinfo.key` → `AttributeError`.

**Expected behavior:** A missing/unresolvable timezone should fall back to a safe default, not crash alarm creation.

**Hypothesis / root cause:** The `or …tzinfo.key` fallback assumes a `ZoneInfo`; the system local tzinfo from `astimezone()` is a `datetime.timezone`. `bmo/pi/services/timer_service.py:283`.

**Suggested action:** Replace the fallback with a guarded default, e.g. `tz_name = _normalize_timezone(timezone_name) or _normalize_timezone(getattr(datetime.datetime.now().astimezone().tzinfo, "key", None)) or DEFAULT_EXISTING_ALARMS_TZ`, or derive the local IANA name a `.key`-free way.

**Environment:** loopback · connected · viewport 480×900.

**Related files:** `bmo/pi/services/timer_service.py:283` (`create_alarm`), `bmo/pi/agent.py:1710-1726` (`_handle_alarm_set`), `bmo/pi/app.py:1547-1561` (`/api/alarms/create`).

**Status vs run 1:** Run 1 reported "setting an alarm via chat always fails" (top #2). **Partially mitigated:** both the dashboard (`/api/alarms/create`) and the dashboard-chat path now pass `_request_client_timezone(default_to_pi=True)`, so the dashboard alarm flow now succeeds (verified: created an 11:59 PM alarm, `target_time_utc` computed, then cancelled). The remaining defect is the latent crash for any caller that reaches `create_alarm` without a resolvable tz (e.g. a voice path, or a future caller). **Not in `docs/logs/BMO-ISSUES-LOG.md`.**

## 8. IDE tab + /ide

### `/ide` Content-Security-Policy blocks the Google-Fonts stylesheet (JetBrains Mono / Inter)

- **Category:** config
- **Severity:** low
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** `/ide` standalone load (headless Chromium console)

**Description:** Loading `/ide` logs a CSP violation: `Loading the stylesheet 'https://fonts.googleapis.com/css2?family=JetBrains+Mono:wght@400;500;700&family=Inter:wght@400;500;600;700&display=swap' violates the following Content Security Policy directive…`. The font stylesheet is blocked, so the IDE renders in fallback fonts. The IDE is otherwise functional — the editor chrome loads, the file tree (home-lab) renders, and the status shows **Connected**.

**Reproduction:**
1. Open `http://127.0.0.1:5000/ide` with DevTools console open.
2. Observe the CSP error for `fonts.googleapis.com`.

**Expected behavior:** Fonts load (no CSP violation), or the IDE ships the fonts from an allowlisted origin.

**Hypothesis / root cause:** The IDE template links Google Fonts, but the `/ide` CSP `style-src`/`font-src` doesn't allow `fonts.googleapis.com`/`fonts.gstatic.com`.

**Suggested action:** Serve the fonts from an already-allowlisted origin (e.g. `cdn.jsdelivr.net`) or self-host them, or extend the `/ide` CSP to permit the Google Fonts origins.

**Environment:** loopback · `/ide` standalone · viewport 1024×700.

**Console output (if any):** `…fonts.googleapis.com/css2?family=JetBrains+Mono…&Inter… violates the following Content Security Policy directive…`

**Screenshot(s):** `screenshots/r2-ide-standalone.png` (IDE loads & shows "Connected"; fonts fall back)

**Status:** **Already tracked** — `docs/logs/BMO-ISSUES-LOG.md:48` and `bmo/docs/phases/PHASE-14-ide-font-csp-and-redirect-doc-truth.md` cover this exact CSP violation (proposed fix: serve fonts from allowlisted `cdn.jsdelivr.net`). Re-confirmed present at `7a266d22`.
