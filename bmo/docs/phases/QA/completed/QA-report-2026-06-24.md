### List items cannot be checked off or deleted from the dashboard (404)

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Home tab -> Lists -> toggle item checkbox / click the item's x delete button

**Description:** On the Home tab Lists card, clicking an item's checkbox (mark done) and clicking its x (delete) both silently fail. The UI shows no change and no error toast; the underlying API calls return 404. The list's core interactions (check off / remove an item) are non-functional from the dashboard. Adding items works (POST 200).

**Reproduction:**
1. Open /bmo (Home tab). Lists card, active list "drugstore".
2. Add an item ("qa-test-item") via the + button -> appears (POST /api/lists/drugstore/items -> 200).
3. Click the item's checkbox -> nothing visibly happens. Network: POST /api/lists/drugstore/items/55d06c8a/check -> 404. Stored item `done` stays false.
4. Click the item's x -> item stays. Network: DELETE /api/lists/drugstore/items/55d06c8a -> 404.
5. (Verified the item id 55d06c8a is the real stored id via GET /api/lists/drugstore.)

**Expected behavior:** Checking an item toggles its done state (strikethrough); the x removes it. Both should return 200.

**Hypothesis / root cause:** API/contract mismatch between the route layer and the service. The routes pass the URL path `<item_id>` to the service, but `ListService.check_item()` and `ListService.remove_item()` match items **by text substring**, not by id:
- `bmo/pi/app.py:2285` `api_list_check_item` -> `list_service.check_item(name, item_id, done)`
- `bmo/pi/app.py:2275` `api_list_remove_item` -> `list_service.remove_item(name, item_id)`
- `bmo/pi/services/list_service.py:99` `check_item(... text ...)`: `if text_lower in item["text"].lower()` (matches on text)
- `bmo/pi/services/list_service.py:79` `remove_item(... text ...)`: matches on text
So an id like `55d06c8a` never matches the item text -> service returns False -> route returns 404. Confirmed: calling DELETE with the item **text** (`/api/lists/drugstore/items/qa-test-item`) returns 200 and removes it. Notes (separate service, id-based) work correctly, which isolates the defect to the list service.

**Suggested action:** Make `check_item`/`remove_item` look items up by `id` (matching how `add_item` mints `id = uuid4()[:8]` and how the frontend addresses them), or change the routes to resolve the id->text before calling the service. Add a regression test for check/delete by id.

**Environment:** external (Cloudflare Access, authenticated) - kiosk off - connected - hardware n/a - desktop 1568px

**Related files:** `bmo/pi/app.py:2275-2293`, `bmo/pi/services/list_service.py:79-111`, `bmo/pi/web/static/js/bmo.js`

**Console output (if any):** none thrown; only the 404s in the network log (silent failure — no user-facing error).

### External chat is non-functional: messages never reach the backend, UI hangs on "BMO is thinking!"

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Chat tab -> type a message ("What is two plus two?") -> Send

**Description:** Over the external URL (https://bmo.mybmoai.work/bmo, the documented off-LAN path), sending a chat message never produces a reply. The UI optimistically renders the user bubble and shows "BMO is thinking!" indefinitely; the input is disabled showing "BMO is thinking!" as placeholder and never recovers. Server-side, the message is **never recorded** in `/api/chat/history` (history stayed at its prior 200 entries; my "two plus two" message is absent). Since the socket handler `on_chat_message` saves the user turn as its first action, the message clearly never reached the handler -- i.e. the socket.io `chat_message` event is not being delivered to the backend over the Cloudflare tunnel.

**Reproduction:**
1. Open https://bmo.mybmoai.work/bmo -> Chat.
2. Type "What is two plus two?" -> Send. User bubble + "BMO is thinking!" appear.
3. Wait 30s+: no reply; input stuck on "BMO is thinking!".
4. `GET /api/chat/history` (server): the message is not present; no assistant turn; no "(interrupted)" stub surfaced either.

**Expected behavior:** The message reaches the backend, the agent replies (or an error bubble "Oops! BMO's brain got fuzzy" appears), and the input re-enables.

**Hypothesis / root cause:** socket.io event delivery over the CF tunnel is failing. Network shows the connection is stuck on **HTTP long-polling** (`transport=polling`, never upgrades to websocket), with **multiple session IDs** and a stale-session **400** on a polling GET (`/socket.io/?...&sid=5xIv...` -> 400). The client-side emit is likely landing on an expired/!sticky polling session and being dropped, so `on_chat_message` never fires. Needs confirmation on the LAN/kiosk path (localhost), which may work; if so this is an external-access-only defect. Trace: `bmo/pi/routes/realtime_ws.py:176` (`on_chat_message`, saves user msg first), socket.io server config in `bmo/pi/app.py`, and the CF tunnel/websocket config.

**Suggested action:** Verify chat on the LAN path; if LAN works, fix websocket upgrade / sticky long-poll over Cloudflare (enable WS in the tunnel, or ensure single-worker/sticky sessions). Add a **client-side send timeout** so a dropped message shows an error instead of hanging (see separate finding).

**Environment:** external (CF Access, authenticated) - desktop - socket.io polling-only - connected (green dot) - kiosk off

**Related files:** `bmo/pi/routes/realtime_ws.py:176-268`, `bmo/pi/app.py` (socketio init), CF tunnel config

**Console output (if any):** no socket errors logged client-side (only the Places warning); failure is silent.

### Entire Music tab is down: music service is None, every /api/music/* call returns 500

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Music tab load + search ("lofi")

**Description:** The Music tab is completely non-functional. `GET /api/music/state` returns **500** and is **polled continuously** (37+ identical 500s captured in one short visit), and `GET /api/music/search?q=lofi` returns **500** -- so search shows no results and silently fails (no user-facing error; the UI just stays on "Search for a song to get started"). Reproduced from localhost too (`curl http://127.0.0.1:5000/api/music/state` -> 500 HTML), so this is an **app-level** failure, not a Cloudflare/external issue.

**Reproduction:**
1. Open /bmo -> Music.
2. Network immediately shows repeated `GET /api/music/state` -> 500.
3. Type "lofi" -> Search -> `GET /api/music/search?q=lofi` -> 500; empty state persists, no error shown.
4. `curl http://127.0.0.1:5000/api/music/state` on the Pi -> HTTP 500.

**Expected behavior:** State returns the player state (or a graceful 503 "music unavailable"); search returns results or an empty list with a visible "no results"/error.

**Hypothesis / root cause:** The music **service failed to initialize and is `None`**, and the route layer dereferences it unguarded. This is documented in the route module itself: `bmo/pi/routes/music_api.py` header -- "The music service is resolved late via `_music()` (so a failed init -> None -> AttributeError -> Flask 500, the pre-extraction behavior)." `api_music_state` is literally `return jsonify(_music().get_state())` (music_api.py:133-135) and `api_music_search` calls `music.search(query)` (music_api.py:25-32) with no None check. So `app.music is None` -> `AttributeError` -> Flask 500 on every call. The underlying init failure (likely the YT Music/VLC/cast backend or its auth/deps at startup) needs investigation in the music service constructor and app startup.

**Suggested action:** (1) Investigate and fix the music service init failure (check app startup logs for the music init exception). (2) Guard the routes: if `_music()` is None, return 503 with a clear message instead of 500. (3) Stop the frontend from hot-polling `/api/music/state` when it 500s (back off), and show a "music unavailable" state rather than a silent empty search.

**Environment:** external + localhost (both 500) - desktop - connected - music backend down

**Related files:** `bmo/pi/routes/music_api.py:25-32,133-145`, the music service constructor + `app.py` music init

**Console output (if any):** server returns the default Flask 500 HTML; the state poll floods the network log with 500s. The frontend also throws an **uncaught** `SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON` plus an Alpine Expression Error in `searchMusic()` -- it parses the 500 HTML page as JSON. So search failure surfaces as uncaught promise rejections, not a handled error.

## 6. Calendar

### Calendar is broken: list, today, next, and create all return 500 (errors hidden as "No events")

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Calendar tab load + "+ Add" -> Create

**Description:** The entire Calendar subsystem errors server-side even though OAuth is valid. `GET /api/calendar/events` -> **500**, `GET /api/calendar/today` -> **500**, `GET /api/calendar/next` -> **500**, and creating an event (`POST /api/calendar/create`) -> **500**. The Calendar tab shows "No events" (the 500 on the events list is **swallowed** and rendered as an empty calendar -- so a user can't tell their events failed to load vs. genuinely having none). Creating a test event reset the form with no event added and no error shown. The Home tab "today's events" card is affected too (it depends on `/today`). Reproduced from localhost (all 500), so this is app-level, not Cloudflare.

**Reproduction:**
1. Open /bmo -> Cal -> shows "No events".
2. `curl http://127.0.0.1:5000/api/calendar/events` -> HTTP 500 (same for `/today`, `/next`).
3. + Add -> fill title/date/time -> Create -> `POST /api/calendar/create` -> 500; form resets, still "No events", no error toast.
4. `curl /api/calendar/auth/status` -> 200 `{authorized:true, "Calendar token is valid"}` -- auth is fine.

**Expected behavior:** Events list/today/next load the user's events; create adds an event and it appears (and on the Home today card). On a backend error the UI shows an error state, not a false "No events".

**Hypothesis / root cause:** The calendar's cached Google API client (`CalendarService._service`) is in a broken/stale state. Evidence: `api_calendar_auth_status` (calendar_api.py:316) succeeds **only because it sets `calendar._service = None` before calling `get_next_event()`** (forcing a rebuild), whereas `/events`, `/today`, `/next`, `/create` use the existing `_service` and all 500. So `get_upcoming_events`/`get_today_events`/`get_next_event`/`create_event` throw a **non-`RuntimeError`** (a Google API/client error) on the stale client. The events route only catches `RuntimeError` (calendar_api.py:37-39) -> returns offline; any other exception becomes a Flask 500. The `/today`, `/next`, `/create` routes have **no try/except** at all (e.g. `return jsonify(_calendar().get_today_events())`), so they 500 outright.

**Suggested action:** (1) Fix the stale `_service`: lazily rebuild the Google client when a call fails (or null `_service` on auth/transport errors and retry), as the auth probe already does. (2) Broaden the route guards: catch the real error class (not just RuntimeError), and on failure return a structured error/offline payload so the UI can show "couldn't load events" instead of a false empty state. (3) Add the same try/except to `/today`, `/next`, `/create`.

**Environment:** external + localhost (both 500) - desktop - calendar OAuth valid - connected

**Related files:** `bmo/pi/routes/calendar_api.py:30-39,41-44,46-50,52-66,316-333`, `bmo/pi/services/calendar_service.py:150-210` (`get_upcoming_events`/`get_today_events`/`create_event`/`_service` handling), `bmo/pi/web/static/js/bmo.js` (calendar render swallows the 500)

**Console output (if any):** server default 500 HTML; UI renders "No events" with no error.

**Could not test (blocked by the above):** editing and deleting an event, recurrence options, Day vs Week views with real data -- all need a readable/creatable calendar. No test event persisted (create 500'd), so no cleanup was required.
