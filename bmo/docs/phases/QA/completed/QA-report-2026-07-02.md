### Plan agent crashes on every request — KeyError: state from unescaped braces in DESIGN_PROMPT

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** chat tab -> agent picker -> Plan agent

**Description:** Selecting the Plan agent and sending any request always returns "I had trouble building that plan — try a different phrasing...". The agent never produces a plan, so the review/approve/cancel flow is unreachable. Server log shows an unhandled `KeyError: state` in `plan_agent.py` `_design()` on every attempt.

**Reproduction:**
1. Chat tab -> agent picker -> select "Plan" (any model).
2. Send e.g. "Plan: add a comment header to bmo.js explaining the file layout".
3. Generic failure bubble; `journalctl -u bmo.service` shows `KeyError: state` at `plan_agent.py:142` (via line 100).

**Expected behavior:** Plan agent returns a structured plan and the plan review/approve UI appears.

**Hypothesis / root cause:** `DESIGN_PROMPT` (plan_agent.py:32) embeds literal JSON examples like `{state:"breathing", color:"purple", brightness:40}` and `{scene:"movie"}`; `DESIGN_PROMPT.format(task=..., scratchpad_context=...)` (plan_agent.py:142) interprets those braces as format fields -> `KeyError: state`. `REDESIGN_PROMPT` likely has the same latent issue.

**Suggested action:** Escape the literal braces (`{{state:...}}`) in DESIGN_PROMPT/REDESIGN_PROMPT, or switch to `string.Template`/manual replace. Add a unit test that calls `_design()` with a trivial task.

**Note:** this is a **regression** -- the same `'state'` KeyError was fixed in the 2026-05-17 Phase 39 bundle (`docs/logs/BMO-RESOLVED-ISSUES.md:2118-2120`, touched `bmo/pi/agents/plan_agent.py`). The endpoint-example text (the brace-bearing JSON) has evidently been reintroduced or re-broken since.

**Environment:** LAN loopback · kiosk off · connected

**Related files:** `bmo/pi/agents/plan_agent.py:32` (DESIGN_PROMPT), `:100`, `:142`

**Console output (if any):** server: `Agent plan failed ... KeyError: state` (plan_agent.py line 142); UI shows generic failure copy.

## 5. Controls tab

### "Unmute" banner CTA cannot fix the condition it warns about (master volume 0%)

- **Category:** UX
- **Severity:** medium
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** controls tab -> master-volume banner

**Description:** The persistent banner reads "Master volume is 0% -- playback will produce no sound. **Unmute**". Clicking Unmute calls `POST /api/audio/unmute`, which only clears the PipeWire mute flag (`wpctl set-mute 0`). With the sink already unmuted but at volume 0.00 (persisted setting `volume.system: 0`), the click is a silent no-op: the banner stays, there is no feedback, and sound remains impossible.

**Reproduction:**
1. Set master/system volume to 0 (settings.json `volume.system: 0`).
2. Load `/bmo` -> banner appears. Click "Unmute".
3. Nothing changes; `wpctl get-volume @DEFAULT_AUDIO_SINK@` still reports `0.00`; banner persists.

**Expected behavior:** The CTA should restore an audible volume (e.g. raise to a floor like 30%), or be labeled per the actual state ("Raise volume"), and give feedback if it cannot.

**Hypothesis / root cause:** Banner condition is volume==0 but the CTA maps to the mute-only endpoint: `bmo/pi/routes/system_api.py:661` (`api_audio_unmute`) never touches volume; wiring in `index.html`/`bmo.js` sends the 0%-volume warning to the unmute action.

**Suggested action:** When volume is 0, additionally call `/api/volume {category:"system", level:<sane default>}`; show a toast on completion.

**Environment:** LAN loopback · kiosk off · connected · master volume 0% (persisted)

**Related files:** `bmo/pi/routes/system_api.py:661`, `bmo/pi/web/templates/index.html`, `bmo/pi/web/static/js/bmo.js`

**Screenshot(s):** `screenshots/r4-40-controls.png`

**Note:** the banner itself triggering on volume==0 is intentional (Phase 39c, `BMO-RESOLVED-ISSUES.md:2129` -- copy adapts between muted and 0%). The gap is only that the CTA action was never split the same way.
