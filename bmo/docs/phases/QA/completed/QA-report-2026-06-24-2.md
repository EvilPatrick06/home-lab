## 1. Home
### List items still cannot be checked off or deleted from the dashboard (404) — REGRESSION-NOT-FIXED

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Home tab -> Lists -> toggle item checkbox / click the item delete (x)

**Description:** On the Home Lists card, checking an item off and deleting it both fail silently in the UI; the underlying API returns 404. Adding items works (POST 200). This is the same high finding as the prior 2026-06-24 pass (against 08772fa6) and is **still present at 12c655a8** — the calendar/music fixes in this build did not touch the list routes.

**Reproduction:**
1. Open /bmo (Home). Active list "drugstore".
2. Add item "qa-test-item" via the + button -> appears (POST /api/lists/drugstore/items 200).
3. Click its checkbox -> `POST /api/lists/drugstore/items/f4761e67/check` returns **404** `{"error":"Item not found"}`; the item is NOT struck through, no error toast.
4. Confirmed directly: `DELETE /api/lists/drugstore/items/f4761e67` (the real item id) -> **404** `{"error":"Item not found"}`, while `DELETE /api/lists/drugstore/items/qa-test-item` (the item TEXT) -> **200** `{"ok":true}` and removes it.

**Expected behavior:** Clicking the checkbox toggles done (strikethrough); clicking x removes the item. Both should 200.

**Hypothesis / root cause (confirmed):** Frontend/backend id-vs-text contract mismatch.
- Frontend `bmo/pi/web/static/js/bmo.js`: `removeListItem(listName, itemId)` (~L4365) DELETEs `/items/${itemId}`; `checkListItem(listName, itemId, done)` (~L4374) POSTs `/items/${itemId}/check`. The template passes `item.id`.
- Routes `bmo/pi/app.py`: `api_list_remove_item` (L2275) calls `list_service.remove_item(name, item_id)`; `api_list_check_item` (L2285) calls `list_service.check_item(name, item_id, done)` — forwarding the URL id straight through.
- Service `bmo/pi/services/list_service.py`: `remove_item(list_name, text)` (L79) and `check_item(list_name, text, done)` (L99, docstring "by text match") match against `item["text"]` (L87/L93/L107), NOT `item["id"]`. So the stable id `f4761e67` never matches any item text -> 404.

**Suggested action:** Make the backend look items up by `id` (the model already stores a stable `id`), OR change the frontend to send `item.text`. The id route is the safer fix. Note also `remove_item` L93 falls back to a **substring** text match (`text_lower in item["text"]`), so a text-based delete of "gav" would also match "gav gav" — fixing to id lookup removes that wrong-item risk too.

**Environment:** external (CF Access) · normal (non-kiosk) · online · viewport 1350-ish · n/a hardware.

**Related files:** `bmo/pi/web/static/js/bmo.js` (~L4365-4385), `bmo/pi/app.py` (L2275-2295), `bmo/pi/services/list_service.py` (L79-110).

**Console output:** none (the fetch failure is swallowed by `catch { console.warn(...) }`; no user-visible error — see separate finding).

**Screenshot(s):** not persisted (browser-driver save-to-disk unavailable this run); reproduction is API-verified above.

## 2. Chat
### Chat agent never responds over the external/Cloudflare path — socket.io handshake is rejected (chat hangs on "BMO is thinking!")

- **Category:** bug
- **Severity:** high
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Chat tab -> send a message ("QA probe: what is 7 times 6?")

**Description:** On the external dashboard (`https://bmo.mybmoai.work/bmo`, authenticated via Cloudflare Access), sending a chat message shows "BMO is thinking!" indefinitely (>20s, never resolves); the input is disabled the whole time and no reply ever arrives. REST endpoints work fine over the same session (lists/notes/music/state all 200), so the page looks healthy, but realtime is dead. This is the same High as the prior pass and is **still present at 12c655a8**.

**Reproduction:**
1. Open `https://bmo.mybmoai.work/bmo` (CF Access authenticated) -> Chat tab.
2. Type any message, Send.
3. UI shows "BMO is thinking!" and never returns a response; connection dot in header goes amber.
4. Server log (`journalctl -u bmo.service`) shows, time-correlated to each page load/connect: `[bmo] [ws] Rejected: BMO_API_KEY required for this client` (two per connect).

**Expected behavior:** A CF-Access-authenticated browser should be able to use realtime chat, OR the UI should clearly surface that realtime is unavailable rather than hanging forever.

**Hypothesis / root cause (confirmed via source + logs):** The socket.io connection auth gate rejects the browser. `bmo/pi/routes/realtime_ws.py` `_authorize` (L40-49) only accepts a client when: `BMO_API_KEY` is unset (L42), the client is trusted-localhost (L44), an `Authorization: Bearer <BMO_API_KEY>` header is present (L46), or socket.io `auth.bmo_api_key` matches (L48). `on_connect` (L129) rejects otherwise and logs the observed message (L132). The external browser authenticates with Cloudflare Access (which satisfies the REST front door) but presents **no** `BMO_API_KEY` to the WS handshake, so every WS connect from the external path is rejected. Chat messages travel over socket.io, so they never reach the agent (`[chat] Restored 200 messages into agent history` confirms the agent itself is healthy). The kiosk works because it connects from `127.0.0.1` (trusted-localhost, L44).

**Suggested action:** Make the WS gate accept the Cloudflare Access identity (e.g. trust the verified `Cf-Access-*`/JWT the same way the REST front door does), or have the dashboard supply `auth: { bmo_api_key }` on the socket.io connection for authenticated sessions. At minimum, surface the rejected-connection state in the UI (see next finding).

**Environment:** external (CF Access) · normal + kiosk · connection dot amber · viewport ~1662 CSS px.

**Related files:** `bmo/pi/routes/realtime_ws.py` (L40-49, L129-132), the socket.io client setup in `bmo/pi/web/static/js/bmo.js`, `bmo/pi/app.py` (BMO_API_KEY gate).

**Console output:** none client-side; server: `[bmo] [ws] Rejected: BMO_API_KEY required for this client`.

### Dashboard repeatedly calls geolocation that is blocked by Permissions-Policy — recurring js-error noise

- **Category:** bug
- **Severity:** medium
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** every page load + every ~15 min (server js-error log)

**Description:** On load and on a ~15-min cadence the dashboard calls `navigator.geolocation.getCurrentPosition`, which is blocked: `[ide] [js-error] Geolocation: getCurrentPosition failed (1): Geolocation has been disabled in this document by permissions policy. at bmo.js`. Each failure is POSTed to `/api/ide/js-error` (200), so it spams the server log (dozens of entries across the day) and is the `/api/ide/js-error` POST seen on every load. Geolocation is disabled by Permissions-Policy (CF / kiosk), so the call can never succeed in this deployment; weather falls back to a fixed location ("Overland Park, Kansas").

**Reproduction:**
1. Load `/bmo`. 2. `journalctl -u bmo.service | grep Geolocation` -> recurring failures, ~every 15 min and on each load.

**Expected behavior:** Either don’t call geolocation when Permissions-Policy disallows it (feature-detect / check `permissions` first), or call it once and cache the "unavailable" result instead of retrying every 15 min and logging each failure as a js-error.

**Hypothesis / root cause:** `bmo.js` calls `getCurrentPosition` unconditionally (for weather/location) and routes the rejection into the global js-error reporter; nothing suppresses the known-blocked case or backs off.

**Suggested action:** Guard the geolocation call behind a Permissions-Policy/permissions-API check; downgrade the expected "disabled by policy" rejection from a reported js-error to a one-time info; stop the 15-min retry.

**Related files:** `bmo/pi/web/static/js/bmo.js` (geolocation/weather), `bmo/pi/routes/ide.py` or app `/api/ide/js-error`.

**Console output:** `Geolocation: getCurrentPosition failed (1): ... disabled ... by permissions policy`.
