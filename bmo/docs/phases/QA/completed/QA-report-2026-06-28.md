## Phase 2 — Chat tab

### CRITICAL: The bmo chat agent is 100% non-functional — every message crashes with `agent is None`

- **Category:** bug
- **Severity:** critical
- **Domain:** bmo
- **Discovered by:** QA Agent
- **During:** Phase 2 — chat tab, sending a message

**Description:** Sending any message to the bmo chat agent fails. In the browser the assistant replies **"Oops! BMO's brain got fuzzy: 'NoneType' object has no attribute 'model_override'"**. The REST fallback `POST /api/chat` returns **HTTP 500**. Server log shows two crash sites, both because the agent reference is `None` at request time:
- WebSocket path — `realtime_ws.py:222` `prev_model_override = agent.model_override` → `AttributeError: 'NoneType' object has no attribute 'model_override'`.
- REST path — `chat_api.py:59` `result = _app().agent.chat(...)` → `AttributeError: 'NoneType' object has no attribute 'chat'`.
This is the headline feature of the dashboard and it is completely down for every user/every message.

**Reproduction:**
1. Open `/bmo` → Chat tab.
2. Type any message (e.g. "what is 2+2?") → Send.
3. Assistant bubble shows "Oops! BMO's brain got fuzzy: 'NoneType' object has no attribute 'model_override'".
4. Or `curl -s -X POST http://127.0.0.1:5000/api/chat -H 'Content-Type: application/json' -d '{"message":"hi"}'` → `500 Internal Server Error`.

**Expected behavior:** The message is routed to the live `BmoAgent` (which boots fine — startup logs `[bmo] Agent: OK` and `Restored 30 messages into agent history`) and a real streamed reply comes back.

**Hypothesis / root cause (high confidence):** A **double-module / wrong-namespace split** caused by the launch method. The systemd unit's `ExecStart=…/venv/bin/python app.py` runs the file as module `__main__`. `init_services()` — which sets the module globals including `agent` (the `global …, agent, …` decl is present) — is called **only** under `if __name__ == "__main__": init_services()` (`app.py:2957-2958`), so it populates **`__main__`'s** globals. But the chat blueprints resolve services late via `_app()`:
```
def _app():
    import app        # imports a SECOND module object "app" (not __main__)
    return app
```
(`chat_api.py:25-26`, `realtime_ws.py:34-36`). `import app` re-executes `app.py` under `__name__=="app"`, so its `__main__` guard is skipped and `init_services()` never runs in that copy — leaving `app.agent` (and `app.voice`, etc.) `None`. `on_chat_message` then does `a = _app(); agent = a.agent` (`realtime_ws.py:183-184`) → `agent is None` → line 222 crash. App.py-native `@app.route` handlers (lists, notes, weather) keep working because they execute against `__main__`'s populated globals; calendar/music blueprints survive because they resolve their services via independent lazy singletons rather than `_app().<attr>`. So the breakage is specific to the `_app()`-resolved agent.

**Suggested action:** Make the running module and the imported `app` the same object, or stop resolving services through a re-imported module. Options: launch via a WSGI/socketio entrypoint where the app module is imported as `app` (e.g. `python -m app` with `init_services()` at import scope, or a `wsgi.py` that imports `app` and calls `init_services()`), OR have `_app()` return `sys.modules["__main__"]` when that is the initialized app, OR store services on `current_app.extensions`/a registry instead of bare module globals. Add a regression test that POSTs `/api/chat` against the *deployed launch path* (the existing endpoint tests likely import `app` directly and therefore never hit the `__main__` split).

**Environment:** external CF-Access (browser) + LAN loopback (REST) · single-user · live process pid 59512 @ 568af48a · launched via systemd `python app.py`

**Related files:** `bmo/pi/app.py:2957-2958` (`__main__` guard), `app.py:505` (`init_services`, `global … agent …`), `bmo/pi/routes/realtime_ws.py:34-36,181-184,222`, `bmo/pi/routes/chat_api.py:25-26,58-59`
