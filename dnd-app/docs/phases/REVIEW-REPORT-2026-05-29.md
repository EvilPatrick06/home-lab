- ✅ **FIXED — Discord→VTT relay delivery guarantee** (protocol overlap). BMO's `vtt_sync.py` now stamps a stable `eventId` (uuid) per event and retries the POST off the request thread (`_send_with_retry`, 4 attempts / 0.5·1.5·3.0s backoff) instead of logging-and-dropping; the VTT bridge (`bmo-bridge.ts`) dedups on `eventId` via a bounded LRU and acks duplicates without re-forwarding, so a retry that lands after the VTT already applied the event can't double-apply it. Schema gained an optional `eventId` (back-compat with pre-retry BMO builds). Tested both sides (5 pytest + 2 vitest). ⚠️ **Needs a BMO restart to take effect** — `sudo systemctl restart bmo-dm-bot bmo-social-bot` (NOT auto-restarted).
- **BMO↔dnd-app HTTP endpoints are unversioned** (`grep -c api/v1 app.py` = 0). A breaking change to `/api/games` or the `:5001` callback would break older in-session clients silently. *Action: add `/api/v1/…` before the next breaking change.*
- **`bmo-peerjs` :9000 (optional self-hosted signaling).** No health surface in dnd-app if the container is down (public PeerJS cloud is the fallback). *Action: surface its health if you rely on the self-hosted path.*
- **Cloud host-migration / DM-handoff over the relay** (protocol overlap). The cloud client now *detects* a host drop and disconnects cleanly (so no silent-broken state), but the session ends rather than electing a new host. True migration needs relay-side (`game_relay.py`) host re-election + a client-promotion handshake (`transferDm` is host-only and needs a live host, so it can't run post-drop). *Action (if wanted): design relay host re-election so a co-DM can be promoted when the host's socket drops.*
