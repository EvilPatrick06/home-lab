### CSP blocks `eval()` — flagged in DevTools Issues at startup

- **Category:** debt
- **Severity:** info
- **Domain:** dnd-app
- **Discovered by:** QA Agent
- **During:** app launch, main menu, DevTools Issues tab

**Description:** On first load (main menu), DevTools Issues shows 1 issue: "Content Security Policy of your site blocks the use of 'eval' in JavaScript." Some bundled code (or a dependency) attempts `eval()`, which the CSP blocks. Blocking eval is good security, but a library relying on it may silently lose functionality.

**Expected behavior:** No code paths should depend on `eval()`; if a dependency uses it, confirm the affected feature still works or remove the dependency.

**Hypothesis / root cause:** A third-party lib (often a templating/expr evaluator or a dev-mode build artifact) calling `eval`/`new Function`. Speculation.

**Suggested action:** Identify the eval caller (DevTools → Issues → expand for source), confirm no feature breaks, or adjust CSP/library.

**Environment:** host=n/a · AI DM off · English · Dark · window: DM (host)

## Phase 2 — Character builder + level-up

### Custom ability score: negative input reverts to arbitrary 15 instead of clamping to min

- **Category:** bug
- **Severity:** low
- **Domain:** dnd-app
- **Discovered by:** QA Agent
- **During:** Character builder → Ability Scores → Custom method

**Description:** In the Custom ability-score method, typing `999` correctly clamps to 20 (max), and `1` is accepted (min). But typing `-5` into a field and tabbing out reverts it to `15` — an arbitrary value, not the min (1) and not the previous value (20). Min/max clamping is inconsistent for negative input.

**Reproduction:**
1. Builder → Ability Scores → Custom
2. Triple-click STR field, type `-5`, press Tab
3. Field shows 15 (expected: clamp to min, i.e. 1)

**Expected behavior:** Out-of-range input clamps to the nearest valid bound (1 or 20), consistently.

**Hypothesis / root cause:** `parseInt("-5")` handling / fallback default of 15 when value fails a `>0` check. Speculation.

**Suggested action:** Clamp custom score input with `Math.max(min, Math.min(max, n))` and treat NaN as previous value.

**Environment:** AI DM off · English · Dark · window: DM (host)

**Related files:** `dnd-app/src/renderer/src/components/builder/` (ability score modal)

### Setting Level field to 10 makes the character uncompletable — spell selection caps don't update

- **Category:** bug
- **Severity:** high
- **Domain:** dnd-app
- **Discovered by:** QA Agent
- **During:** Character builder → Spells tab, after typing 10 into the Level field

**Description:** Build a level-1 Wizard, satisfy all requirements (3/3 cantrips, 4/4 spellbook → "Save Character" enabled). Then type `10` into the Level field. The header correctly updates to require **5 cantrips** and **15 spellbook** spells ("Select all 5 cantrips (3/5 chosen)", "Select all 15 prepared spells (4/15 chosen)"), HP recalculates to 62, and the per-level "CLASS PER LEVEL" panel appears. **But the spell-selection logic still enforces the level-1 caps (3 cantrips, 4 spellbook):** clicking any additional cantrip or spell checkbox does nothing (count stays 3/5 and 4/15). Removing a selected spell (4→3) then re-adding it works (3→4), but you can never exceed the old cap. Result: the level-10 character can **never** satisfy validation and **cannot be saved** — directly setting a high starting level yields a permanently-blocked build.

**Reproduction:**
1. New Character → Wizard, fill foundation, About/Specials/Languages
2. Spells: pick 3 cantrips + 4 spellbook → Save enabled
3. Set Level field to 10
4. Try to add a 4th/5th cantrip or 5th+ spellbook spell — checkbox no-ops; counters stuck at 3/5 and 4/15
5. Remove one, re-add → works back up to old cap only

**Expected behavior:** Changing the Level field should recompute the selection caps (max cantrips/prepared/spellbook) to match the new level so the character can be completed, OR the Level field should be read-only and leveling done only via the level-up flow.

**Hypothesis / root cause:** The "required count" display is derived from the new level, but the checkbox `disabled`/max-selection guard still reads a cap memoized from the initial (level-1) class state and isn't recomputed on Level change. Speculation.

**Suggested action:** Recompute cantrips-known / prepared / spellbook limits whenever level (or per-level class) changes; add a test that builds a level-10 caster via the Level field and asserts it can be saved.

**Environment:** AI DM off · English · Dark · window: DM (host) · Wizard, Level set to 10 via field

**Related files:** `dnd-app/src/renderer/src/components/builder/` (spell selection step + level/derived-stats hook)

### PixiJS v8 deprecation warning on map render (Container.name removed)

- **Category:** debt
- **Severity:** low
- **Domain:** dnd-app
- **Discovered by:** QA Agent
- **During:** entering in-game / map (PixiJS canvas) render

**Description:** On loading the in-game map, DevTools logs a PixiJS deprecation warning: "Container.name property has been removed, use Container.label instead. Deprecated since v8.0.0" (plus "3 hidden" additional warnings batched). The app uses PixiJS 8 (per About) but still sets `Container.name`, which is a no-op in v8 — any code relying on looking up containers by `.name` may silently fail.

**Suggested action:** Replace `.name` with `.label` on PixiJS containers in the map renderer; audit any `getChildByName`/name-based lookups.

**Environment:** AI DM on (Ollama) · English · Dark · window: DM (host)

**Console output:** `PixiJS Deprecation Warning: Container.name property has been removed, use Container.label instead. Deprecated since v8.0.0` (vendor-pixi chunk)
