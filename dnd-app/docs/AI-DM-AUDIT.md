## Standing design warnings (migrated — keep enforced)

- **bmo: DO NOT add `concurrent.futures.ThreadPoolExecutor`/`ProcessPoolExecutor` inside `app.py`.** `gevent.monkey.patch_all()` (app.py line 12) does not patch `concurrent.futures` — pool workers are real OS threads whose blocking I/O stalls the whole gevent loop. Existing `threading.Thread(daemon=True)` sites are greenlets (safe). Use `gevent.pool.Pool(N).spawn()` for pooled work; `subprocess.Popen` for CPU-bound. Files: `bmo/pi/app.py:12` + all `threading.Thread` sites. *(migrated: BMO-SUGGESTIONS-LOG gotcha, high)*
- **bmo: DO NOT use `requests` in LLM-streaming-path routes — prefer `httpx`** (already a dependency via `agents/mcp_client.py`). `requests.Session` holds the gevent loop during stalled upstream streams; the `os.system('curl …')` workaround in `services/cloud_providers.py` exists exactly because of this — keep it until a load-tested `httpx.stream` replacement lands. *(migrated: BMO-SUGGESTIONS-LOG gotcha, medium)*

## Performance / reliability — better ways for things that already work *(web-researched 2026-06-10)*

- **Set `keep_alive` and exploit Ollama's prefix (KV) cache — measured ~17.7× prefill speedup on cache hits.** Ollama reuses prefill computation when a request shares a byte-identical prefix with the previous one AND the model is still loaded; default unload is 5 min idle, which wipes the cache (then the next message re-pays the full ~9.6k-token prefill — the exact pain behind the timeout work). Do: (1) pass `keep_alive: -1` (or `60m`) in chat requests (`dnd-app/src/main/ai/ollama-client.ts:96,230`); (2) order the prompt static-first — fixed system prompt → semi-static campaign/character data → volatile `[GAME STATE]`/`[GAME TIME]` LAST — because any early changed byte busts the cache; (3) note `[GAME TIME] Total seconds: N` (state-snapshot.ts) changes every message — keep it late in the prompt; (4) never vary `num_ctx` or the options block between requests — a changed option counts as a new model configuration and triggers a reload that wipes the KV cache (the API `keep_alive` param overrides `OLLAMA_KEEP_ALIVE`). Cache invalidates at the FIRST differing byte, so even a timestamp early in the system prompt forces full re-prefill of everything after it. Sources: [Ollama prompt caching](https://leanpub.com/read/ollama/prompt-caching), [KV cache & scheduling](https://jonathanding.github.io/llm-learning/en/articles/ollama-kv-cache-scheduling/), [keep-alive guide](https://mljourney.com/ollama-keep-alive-and-model-preloading-eliminate-cold-start-latency/), [Ollama FAQ](https://docs.ollama.com/faq).

- **KV-cache quantization to fit a bigger `num_ctx`.** `OLLAMA_FLASH_ATTENTION=1` (the prerequisite) plus `OLLAMA_KV_CACHE_TYPE=q8_0` halves KV memory with negligible quality loss (q4_0 quarters it; ~2 GB saved on a 7B at 32k ctx) — pairs with the num_ctx fix so an 8k–16k window fits consumer VRAM, and keeps the cache from spilling the model into CPU offload mid-session. Caveat: some models (Gemma 3) had slowdowns with KV quantization. Sources: [K/V cache quantization](https://mitjamartini.com/posts/ollama-kv-cache-quantization/), [ollama#9683](https://github.com/ollama/ollama/issues/9683).

- **Use Ollama structured outputs (`format` = JSON schema, XGrammar constrained decoding) instead of regex-harvesting `[DM_ACTIONS]`/`[STAT_CHANGES]` from prose.** Guarantees 100% schema compliance at the decoder level — eliminates the whole repairJson/validation-reject class for small local models. Hybrid fit for this app: keep narration freeform, then make ONE follow-up structured call ("emit the actions for what you just narrated") with `format: <zod-derived JSON schema>` + low temperature — or use it only on the parse-failure retry path first. Known-broken corner (upstream issues): `format` is NOT enforced when streaming with thinking enabled ([ollama#14440](https://github.com/ollama/ollama/issues/14440)) and streamed tool-call deltas can be lost ([#12557](https://github.com/ollama/ollama/issues/12557)) — run the extraction call with `stream: false`. Sources: [Ollama structured outputs](https://ollama.com/blog/structured-outputs), [constraining LLMs with Ollama](https://www.glukhov.org/llm-performance/ollama/llm-structured-output-with-ollama-in-python-and-go/), [structured outputs guide](https://techsy.io/en/blog/llm-structured-outputs-guide).

- **Streaming sentence-chunked TTS for Discord VC (fixes truncation + latency + rate-limit drops in one design).** Split narration at sentence boundaries as it arrives, feed chunks to a local streaming TTS, and play through the existing `_play_audio` queue-wait — no more `text[:500]`, no 3s-cooldown drops, ~2–4s to first audio. Local models: Kokoro (82M params, <2GB, streaming, existing Discord-bot reference impl) or Piper (lighter/faster, Pi-friendly) replace the cloud `fish_audio_tts` dependency + its rate limits. Concrete stack: pipe the live LLM token stream through [stream2sentence](https://github.com/KoljaB/stream2sentence) (handles abbreviations/quotes; time-based mode yields partial fragments so audio never stalls) or [RealtimeTTS](https://github.com/KoljaB/RealtimeTTS) (wraps the whole pattern); synthesize via [Kokoro-FastAPI](https://github.com/remsky/Kokoro-FastAPI)'s OpenAI-compatible streaming endpoint (~300ms first chunk on GPU; chunking tunable via `TARGET_MIN/MAX_TOKENS`); keep Piper as the Pi-CPU fast path for short reactive lines. Sources: [RealtimeTTS](https://pypi.org/project/realtimetts/) (stream-of-text → stream-of-audio with sentence chunking), [Kokoro TTS Discord bot](https://github.com/Viker/Kokoro-TTS-Discord-Bot), [Kokoro guide](https://docs.clore.ai/guides/audio-and-voice/kokoro-tts), [Piper](https://tts.ai/text-to-speech/?model=piper).

- **Index the campaign's OWN content into RAG, not just the 5e rulebooks.** Foundry's RPGX AI Librarian pattern: ingest+structure the world's journals/handouts/NPC notes so the AI answers from the campaign's documents. The app already has the search-engine/RAG infra for rules and a memory manager — extending indexing to campaign journals/handouts/lore would close the "AI doesn't know my world doc" gap. On the rules side, 5e queries are exact-match-shaped (spell/condition/feature names like "Grappled", "Sneak Attack") where pure vector search underperforms — hybrid BM25+vector retrieval with markdown-header chunking and contextual chunk headers ("PHB > Ch.9 Combat > Opportunity Attacks" prepended to each chunk) is the current-standard fix. Sources: [RPGX AI Assistant](https://foundryvtt.com/packages/rpgx-ai-assistant), [RPGX AI Librarian](https://foundryvtt.com/packages/rpgx-ai-librarian).

- **Upgrade the flat-JSON memory files toward entity/temporal memory.** Current memory-manager stores flat JSON lists (NPCs, places, rulings, summaries). 2025-26 agent-memory research + production systems (Zep temporal knowledge graphs, Mem0 scalable agent memory, hierarchical memory orchestration) show recall quality jumps when memories carry entities + relations + timestamps with retrieval/decay policies — a natural evolution for long campaigns where "what does Volo know about the party as of session 12" matters. Sources: [Zep/Mem0 + survey](https://www.emergentmind.com/topics/memory-mechanisms-in-llm-based-agents), [agent-memory paper list](https://github.com/Shichun-Liu/Agent-Memory-Paper-List), [hierarchical memory orchestration](https://arxiv.org/pdf/2604.01670).

- **"Suggest tactical action" combat assistant (PF2e AI Combat Assistant pattern).** Per-turn LLM suggestion of the mechanically-sound action for the active monster — in this app it could pre-fill the AI DM's own combat turn or advise a human DM. Foundry's mookAI goes further and fully automates low-INT monster turns (vision-based targeting, collision-free pathfinding, move-into-range + attack + end turn, optional auto-trigger on initiative for goblin-tier mooks) — the proven split is a deterministic action engine for mechanics with the LLM used only to narrate the chosen action, which avoids rules hallucination and fixes solo play forcing the player to run both sides of combat. Sources: [AI Combat Assistant PF2e](https://github.com/AI-DM-Foundry/AI-Combat-Assistant-Pf2e), [mookAI](https://foundryvtt.com/packages/mookAI-12).
- **Context-inspector panel (Phils AI Assistant "prompt engineer bridge" pattern).** The app already computes a per-request token breakdown (`getLastTokenBreakdown`, `context-builder.ts`) — surface it in a DM-facing debug panel ("what did the AI actually see?") to make context bugs (like truncation) visible instead of mysterious. Source: [Phils AI Assistant](https://foundryvtt.com/packages/phils-ai-assistant).

## Engine / architecture patterns *(web-researched 2026-06-10, fleet round 2)*

- **Move durable world state out of the transcript into a queryable store — LLM emits deltas, engine owns truth.** The strongest recurring pattern in working LLM-GM projects: rooms/NPCs/inventory/opinions live in a store (graph DB or plain JSON), each turn injects only the relevant slice, and the model returns structured deltas that deterministic code applies. Neo4j's agentic-memory MUD is a worked example (per-NPC `THINKS_OF` opinion edges that persist across encounters, spatial nodes for consistent backtracking, lazy world generation). Sources: [Neo4j agentic-memory MUD](https://neo4j.com/blog/developer/agentic-memory-multi-user-dungeon/), [VirtualGameMaster](https://github.com/Maximilian-Winter/VirtualGameMaster).
- **Summarize at scene boundaries with layered memory (scene → session → campaign), not token thresholds.** CALYPSO (AIIDE '23) keys compaction to narrative structure: scene transitions are natural compression points, and a prefix that only changes at scene boundaries means every mid-scene turn stays a warm KV-cache hit — threshold-based compaction rewrites the prefix at arbitrary mid-scene moments and busts the cache. Synergizes directly with the keep_alive/prefix-cache work above. Sources: [CALYPSO (arXiv 2308.07540)](https://arxiv.org/abs/2308.07540).
- **Agentic "director" layer separate from the narrator.** A planner agent that reasons over pacing, tracks secrets/foreshadowing, frames scenes, and decides when to trigger encounters — distinct from the prose narrator. Research on solo-RPG GMs (arXiv 2502.19519, 2025) found the multi-agent ReAct GM significantly improved immersion/curiosity vs a prompt-only GM; counters the two classic AI-DM failure modes (aimless wandering, railroading). Source: [Static vs. Agentic Game Master AI (arXiv 2502.19519)](https://arxiv.org/abs/2502.19519).
- **Structured quest objectives with auto-checked completion.** RPGGO's engine treats goals as first-class structured objects a checker agent validates against the transcript, gating chapter advancement — fixes drifting pacing and gives a real quest log (objective ticks, chapter transitions) instead of relying on the narrator's memory. Complements the director agent. Source: [RPGGO text-to-game framework](https://blog.rpggo.ai/2025/02/21/technical-overview-rpggos-text-to-game-framework-for-ai-rpg/).
- **Keyword/state-triggered world-info injection (SillyTavern World Info mechanics).** Deterministic, zero-embedding retrieval that pairs well with small local models: lorebook entries fire when keywords appear within a configurable scan depth, with priority resolution and state-toggled variants (town "peaceful" vs "under attack"). The WorldInfo-Recommender extension additionally drafts/updates entries from chat context. Sources: [SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/), [WorldInfo-Recommender](https://rpfiend.com/sillytavern-lorebooks-worldinfo-recommender-by-bmen25124/).
- **Dice-driven oracle/GM-emulator randomness feeding the LLM.** LLMs have a "yes-and" agreeability bias; solo-RPG practice fixes it with oracles. Inject Mythic-style yes/no oracle results, random event/twist tables, and scene-alteration tests into the prompt as authoritative facts the narrator must honor — genuine surprise the model can't smooth over, and the existing dice system makes the rolls visible/trustworthy. Sources: [Mythic GME Digital](https://jasonholtdigital.itch.io/mythic-gme-digital), [AI GM emulator how-to](https://oracle-rpg.com/2025/01/how-to-create-an-ai-gm-emulator-for-free-with-chatgpt/).
- **Design extraction schemas for small-model reliability.** 7–9B models handle constrained decoding reliably only on simple schemas (flat array of `{type: enum, target: string, value: number}`, few optionals, temperature 0, schema echoed in the prompt); deeply nested many-optional schemas produce field hallucination and premature termination. Constrained decoding guarantees shape, not truth — validate extracted values against game state before applying. Sources: [Ollama structured outputs docs](https://docs.ollama.com/capabilities/structured-outputs), [structured-output issues writeup](https://www.glukhov.org/post/2025/10/ollama-gpt-oss-structured-output-issues/).
- **Per-task model routing + mid-campaign model swap UI.** Route mechanics adjudication, entity extraction, goal-checking, and summarization to a small fast model; reserve the large model for narration — directly mitigates the local-CPU prefill pain by keeping big-prompt calls rare. Reviewers single out mid-campaign model swap as a standout competitor feature. Sources: [AI Realm](https://airealm.com/), [FoundryAI](https://foundryvtt.com/packages/foundry-ai).
- **Speculative decoding is still NOT in stock Ollama.** If decode speed matters, llama.cpp's `llama-server --model-draft` (OpenAI-compatible endpoint; Qwen3-0.6B drafting for 8B ≈ 1.9×; predictable RPG prose has high acceptance rates) can sit behind the existing client with minimal change. Sources: [ollama#5800](https://github.com/ollama/ollama/issues/5800), [llama.cpp speculative docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md).

## Product feature ideas *(web-researched 2026-06-10, fleet round 2)*

- **Per-NPC voice casting for Discord/TTS narration.** Assign a distinct TTS voice per NPC (auto-assigned on first appearance from a pool keyed by race/gender/age, player-overridable) so dialogue is audibly distinct from narration; requires tagging dialogue spans with speaker IDs in AI output — pairs naturally with entity records. Sources: [fables.gg](https://fables.gg/), [FoundryAI](https://foundryvtt.com/packages/foundry-ai).
- **Campaign Q&A assistant + "previously on" session recaps.** A side-channel assistant (separate from the in-fiction DM) that reads campaign data and answers private context-aware questions ("what did the innkeeper say about the mine?") plus one-click recaps at session start — CALYPSO research found DMs valued exactly this distillation. BMO already has a `session_recap` agent to build on. Sources: [FoundryAI](https://foundryvtt.com/packages/foundry-ai), [Archivist AI](https://www.myarchivist.ai/ai-dungeon-master/foundry-vtt), [CALYPSO](https://arxiv.org/abs/2308.07540).
- **Text-to-battlemap generation with walls/doors/light metadata.** Let the AI DM emit a structured map spec (rooms, terrain, walls, doors, light sources, spawn points) rendered by a procedural tile engine — every AI-generated encounter gets a fog-of-war-ready tactical map instead of a blank grid. Dungeon Alchemist is the benchmark; pure image-model generators prove demand but lack metadata, so the structured-spec approach (LLM-friendly JSON) is the better variant. Sources: [Dungeon Alchemist](https://www.dungeonalchemist.com/).
- **Asynchronous play-by-post campaign mode with Discord turn pings.** Scheduling kills multiplayer campaigns; an AI DM is always available. A per-scene turn queue persisted on the 24/7 Pi + the existing Discord integration pinging whoever is up enables async play — a real differentiator vs session-only VTTs. Source: [fables.gg](https://fables.gg/).
- **Shareable scenario/world seed packs.** A versioned export/import format for campaign seeds (world lore + opening scene + quest hooks + encounter tables + tone instructions) plus a few curated built-in packs — gets most of the marketplace value with no hosted infrastructure, and seeds slot into the lore/entity system. Sources: [AI Dungeon scenarios](https://play.aidungeon.com/), [2026 AI-DM landscape](https://storyroll.app/blog/best-ai-dungeon-masters-2026).
- **Cinematic "scene mode" toggle (Alchemy-style theater of the mind).** Full-bleed scene view — evocative art, ambient soundscape, particle effects, no grid — with one-click toggle back to the tactical map when combat starts. Alchemy VTT built its product on exactly this split: scenes for story, grid for fights. Source: [Alchemy RPG](https://alchemyrpg.com/).
- **Built-in safety tools: lines/veils as hard AI constraints + X-card rewind.** No surveyed AI-DM product does this well — a differentiator. Session-zero panel capturing lines (never appears) and veils (off-screen only) injected as non-negotiable system-prompt constraints, plus an X-card command (chat button / Discord reaction) that halts the scene, regenerates the offending content, and appends the topic to the campaign ban list. Sources: [Lines & Veils](https://blog.roll20.net/posts/guest-blog-an-introduction-to-lines-and-veils/), [safety tools overview](https://slyflourish.com/safety_tools.html).
- **Barge-in/cancellation through the whole narration pipeline.** When a player acts mid-narration, abort LLM generation, flush the sentence buffer, stop in-flight TTS, and cut Discord playback — otherwise the bot narrates a stale scene over the new one. One cancellation token per DM turn threaded through the Ollama stream, the chunk queue, the TTS request, and `voice_client.stop()`. Sources: [voice-pipeline architecture](https://www.retellai.com/blog/how-real-time-voice-ai-works-stt-llm-tts).
