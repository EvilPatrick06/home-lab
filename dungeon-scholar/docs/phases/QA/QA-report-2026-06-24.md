### Repeated "TypeError: Failed to fetch" from Supabase token refresh on load
- **Category:** bug
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Phase 0 — first load of #/home, signed-out
**Description:** On initial load the console logs `TypeError: Failed to fetch` five times over ~5s, originating from Supabase GoTrue `so._refreshAccessToken` → `_callRefreshToken`. The UI is unaffected, but it's recurring console-error noise (a retry loop) that fires even with no signed-in session.
**Reproduction:**
1. Open https://evilpatrick06.github.io/home-lab/#/home with DevTools console open (signed-out).
2. Observe 5 repeated `Failed to fetch` errors from the token-refresh path.
**Expected behavior:** No token refresh attempts (or a single, caught, non-error-level log) when there is no session / sync is unconfigured/unreachable.
**Hypothesis / root cause:** Supabase client schedules `_callRefreshToken` and retries on network failure; the rejection isn't swallowed to a debug log. Likely in the supabase sync service init.
**Suggested action:** Guard refresh on presence of a session; downgrade caught network failures to a single debug log.
**Related files:** `dungeon-scholar/src/services/` (supabase sync), `dungeon-scholar/src/features/` auth init
**Console output:** `TypeError: Failed to fetch ... so._refreshAccessToken ... _callRefreshToken`

## 1 Routing & navigation

### Navigating to a lazy route (Library) crashes into the error boundary until a hard refresh — stale service-worker shell
- **Category:** bug
- **Severity:** high
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Phase 1 routing — first navigation from #/home to #/library (SPA already loaded, no reload)
**Description:** With the SPA already loaded on #/home, navigating to #/library renders the global error boundary ("⚠ SOMETHING WENT WRONG / A spell misfired in this chamber"). Expanding "Technical details" shows: `Failed to fetch dynamically imported module … DpP_q3kX.js`. A normal in-app nav therefore dead-ends on a crash screen. After a hard reload (Ctrl+Shift+R) on #/library, the screen loads correctly ("The Grand Library", tome list, all controls). So the failure is the cached app shell requesting a code-split chunk that no longer exists on the server.
**Reproduction:**
1. Load https://evilpatrick06.github.io/home-lab/#/home (let the SW-cached shell serve it).
2. Click the Library nav icon / navigate to #/library WITHOUT hard-refreshing.
3. Error boundary appears; Technical details = "Failed to fetch dynamically imported module ... DpP_q3kX.js".
4. Hard reload (Ctrl+Shift+R) → Library now loads fine.
**Expected behavior:** In-app navigation to a code-split route always loads (or self-recovers) without showing the crash screen, even after a new deploy changed chunk hashes.
**Hypothesis / root cause:** The Workbox/service-worker precache (or an HTTP-cached `index-*.js`) is serving a STALE app shell whose lazy-import graph references an old hashed chunk (`DpP_q3kX.js`) that the latest GitHub-Pages deploy (dd0b1d97) no longer ships → the dynamic `import()` 404s → error boundary. Only a hard reload bypasses the SW and fetches the current shell + chunks. Likely the SW lacks a skipWaiting/clients.claim + reload-on-new-version flow, and there is no `vite:preloadError`/failed-dynamic-import retry handler.
**Suggested action:** (a) Add a global `window.addEventListener('vite:preloadError', …)` (or a dynamic-import retry) that force-reloads on a failed chunk fetch; (b) ensure the service worker takes control of new versions promptly (skipWaiting + clients.claim + an "update available → reload" prompt); (c) confirm GitHub Pages isn't long-caching `index.html`.
**Environment:** signed-out · Dark · desktop (~1568px) · active AWS tome loaded · SW-cached shell (pre-hard-refresh)
**Related files:** `dungeon-scholar/src/router/` (lazy route imports), service-worker/Workbox config (`vite.config.js` / PWA plugin), `dungeon-scholar/src/App.jsx` (error boundary)
**Console output:** `Failed to fetch dynamically imported module: https://evilpatrick06.github.io/home-lab/assets/...DpP_q3kX.js`
**Screenshot(s):** (capture-to-disk unavailable this run — see Could not test; error-boundary text + Technical details transcribed above)

## 4 Dungeon delve

### Dungeon delve introduces a full-page vertical scrollbar instead of fitting the viewport
- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Phase 4 — entering a delve (#/dungeon → Begin the Delve), desktop ~1568×900, Dark
**Description:** Once inside a delve, the top-down canvas + HUD render taller than the viewport, so the browser shows a persistent right-edge vertical scrollbar during play. A dungeon screen is the kind of view that should be self-contained to the viewport; needing to scroll the page during real-time movement is awkward (the player sprite/foe can sit below the fold).
**Reproduction:**
1. #/dungeon → Begin the Delve.
2. Observe the page-level vertical scrollbar; content extends below the viewport.
**Expected behavior:** The delve view fits within the viewport (its own internal layout), no page-level scroll during play.
**Hypothesis / root cause:** The delve canvas/HUD container isn't height-capped to `100vh`/`100dvh` (or the global header still occupies space above the canvas), so total height overflows. Likely in the dungeon delve screen/layout component.
**Suggested action:** Cap the delve container to the viewport height (account for the header) and let the map pan internally rather than the page.
**Environment:** signed-out · Dark · desktop · active AWS tome
**Related files:** `dungeon-scholar/src/features/` (dungeon/delve screen + canvas wrapper)
**Screenshot(s):** (capture-to-disk unavailable — scrollbar visible in delve view; described above)
