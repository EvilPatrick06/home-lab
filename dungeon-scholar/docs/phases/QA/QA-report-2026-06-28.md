## 2 Library & tomes

### Inconsistent post-import behavior: CSV deck import auto-activates the new tome, but Paste-Tome-Text import does not

- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** library → importing via "Import Deck (CSV/Quizlet)" vs "Paste Tome Text"

**Description:** Importing via "Import Deck (CSV/Quizlet)" immediately makes the new tome the **active** tome ("Imported 8 cards into a new tome" and the home shows it as ACTIVE TOME). Importing via "Paste Tome Text" does **not** activate it — it toasts "Tome added: '…' — switch from the Library when ready" and leaves the previous tome active. Two adjacent import entry points behave differently, which is surprising (a user who pastes a tome and immediately opens a study mode studies the *old* tome).

**Reproduction:**
1. With tome A active, use Import Deck (CSV) → new tome becomes active.
2. With tome A active, use Paste Tome Text → new tome is added but A stays active.

**Expected behavior:** Pick one consistent rule for "after import, is the new tome active?" across all import paths (or make both prompt/confirm).

**Hypothesis / root cause:** The deck-import handler calls the activate/switch action after `addTomeToLibrary`; the paste-JSON handler only adds to the library without switching.

**Suggested action:** Align the two import handlers (e.g. both activate the freshly imported tome, or both just add + toast).

**Environment:** Light theme · desktop · cloud-sync on

**Related files:** `dungeon-scholar/src/features/library/ImportDeckModal.jsx`, `dungeon-scholar/src/hooks/useAppModals.js`, `dungeon-scholar/src/features/player/usePlayerActions.js`

## 3 Study modes

### "The Redeemed" title (+gold) unlocks just by opening an empty Mistake Vault — even with no tome and nothing ever banished

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** routing walk → navigating to `#/vault` with no active tome

**Description:** Navigating to the Mistake Vault fired a "Title Unlocked: The Redeemed" toast and bumped gold 226 → 276, despite there being **no active tome loaded** and the player never having banished a single mistake. The title `vaultkeeper` ("The Redeemed — Banish all foes from your Tome of Failures") is meant to reward *clearing* a populated vault, but it is granted for merely viewing an empty one.

**Reproduction:**
1. Use a profile with >10 lifetime answered questions (here: 88/124).
2. With no tome loaded, navigate to `#/vault`.
3. Observe: "Title Unlocked: The Redeemed" toast + gold increases by 50; `unlockedTitles` now contains `vaultkeeper`.

**Expected behavior:** The title should unlock only after the player actually accumulates mistakes in a tome's vault and then clears them — not on first visit to an empty one, and not when no tome is active.

**Hypothesis / root cause:** `MistakeVault.jsx:15-20` runs an unconditional `useEffect` that fires before the `if (!courseSet) return` early-out (hooks always run):
```js
useEffect(() => {
  if (vault.length === 0 && playerState.totalAnswered > 10) {
    checkAchievement('vault_clear');
    unlockSpecialTitle('vaultkeeper');
  }
}, [vault.length]);
```
An empty vault (`vault.length === 0`) is treated as "all foes banished," which is vacuously true for a vault that was never populated, and the guard ignores `courseSet` being null. Title def: `game/titles.js:25`.

**Suggested action:** Gate the unlock on having actually had mistakes that were then cleared (e.g. track a per-tome `vaultEverHadEntries` / `banishedCount > 0` flag), require an active `courseSet`, and only run the effect when a tome is loaded.

**Environment:** signed-in (Supabase token present) · cloud-sync on · Oracle n/a · Dark theme · desktop · no tome loaded

**Related files:** `dungeon-scholar/src/features/study/MistakeVault.jsx` (L15-20), `dungeon-scholar/src/game/titles.js` (L25)

### Light theme: flashcard QUESTION text is dark-on-dark and nearly illegible

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** study modes → Flashcards, Light theme, imported tome
- **Status:** likely shares a root cause with the known "Light-theme dark-on-dark" finding in `QA-report-2026-06-24-2.md` — this is a concrete, still-present instance on build `index-Dy2bw_1f.js`.

**Description:** On the Flashcards front ("THE QUESTION"), the question text is rendered in a dark amber/brown (`oklch(0.279 0.077 45.635)`) on the card's dark-navy gradient background (`linear-gradient(135deg, rgba(12,24,41,0.85), rgba(6,12,20,0.95))`). The result is near-zero contrast — the question ("Author of Hamlet?") is barely readable. The "THE QUESTION" label (blue) and the "Touch the scroll to reveal" hint (gold) are fine; both the question (front) and the revealed answer text (back, e.g. "Shakespeare") are affected — only the blue label and gold hint keep contrast.

**Reproduction:**
1. Set Light theme (Home → Visual Theme → ☀ Light) — or use a profile already in Light (this profile is `data-theme="light"`).
2. Load any tome, open Flashcards.
3. Observe the question text is dark-on-dark on the card front.

**Expected behavior:** The flashcard front's question text must keep a light/high-contrast color because the card background stays dark navy in **both** themes.

**Hypothesis / root cause:** The card front background is a fixed dark gradient regardless of theme, but in Light theme a broad rule overrides the intended `text-amber-50` (light) utility on the question `div` to a dark amber value (computed `color: oklch(0.279 0.077 45.635)` despite `class="text-xl text-amber-50 italic"`). The Light-theme color override is being applied to text that sits on a theme-invariant dark surface. Fix by scoping the Light-theme text override so it does not hit elements on dark card surfaces, or by theming the card background too.

**Suggested action:** Either keep the flashcard front text light in Light theme (e.g. a theme-invariant class on the card), or give the card a light background in Light theme so the dark text is legible.

**Environment:** signed-in · cloud-sync on · Oracle n/a · **Light theme** · desktop · imported tome loaded

**Related files:** `dungeon-scholar/src/features/study/` (flashcard front component) + the global Light-theme stylesheet/theme tokens (`src/index.css` / theme CSS)

### Supabase auth token-refresh failure loop spams the console with `TypeError: Failed to fetch` on every page

- **Category:** bug
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** routing walk (console health) — present on every screen while a stale Supabase session is in `localStorage`
- **Status:** already tracked — prior reports `QA-report-2026-06-24-2.md` / `-3.md` and `PHASE-02` (Supabase token-refresh console noise). Re-confirmed on build `index-Dy2bw_1f.js`; still present.

**Description:** A signed-in Supabase session (`sb-wivnzcbufpqdjwycampb-auth-token` in `localStorage`) drives a background access-token refresh that fails repeatedly: the console accumulates `TypeError: Failed to fetch` from `_refreshAccessToken`/`_callRefreshToken`, escalating to `AuthRetryableFetchError: Failed to fetch`. Roughly one error every few seconds (retry/backoff), independent of which screen is open. UI remains usable (local-first), but the console is continuously noisy, which masks real errors during QA.

**Reproduction:**
1. Load the live app while a Supabase auth token is in `localStorage`.
2. Open DevTools → Console.
3. Observe repeated `TypeError: Failed to fetch` (and `AuthRetryableFetchError`) entries on every screen.

**Expected behavior:** A failed token refresh (Supabase project unreachable/paused, or offline) should be caught and surfaced once as a quiet, throttled warning — not an unbounded stream of uncaught errors.

**Hypothesis / root cause:** The Supabase client's auto-refresh timer keeps retrying an unreachable auth endpoint and the rejections are not swallowed by the app. Likely the cloud-sync service does not disable `autoRefreshToken` / catch the retryable fetch error when the backend is down. (Bundled/minified at `index-Dy2bw_1f.js:25` `Co._refreshAccessToken`.)

**Suggested action:** Wrap the refresh path, throttle/dedupe the logging, and stop the auto-refresh loop after N consecutive failures (or when `navigator.onLine` is false); consider clearing an invalid session.

**Environment:** signed-in (stale Supabase session) · cloud-sync on · Dark theme · desktop · all screens

**Related files:** `dungeon-scholar/src/services/` (Supabase sync/client wiring)

**Console output (if any):** `[ERROR] TypeError: Failed to fetch ... Co._refreshAccessToken ... Co._callRefreshToken`; `[ERROR] AuthRetryableFetchError: Failed to fetch`

## Could not test

The following were not exercised due to genuine environment blockers in this unattended browser-only run (not skipped for convenience):

- **Mobile (375 px) / tablet (768 px) viewport matrix.** The browser viewport could not be resized below desktop width in this environment — `resize_window` was accepted but `window.innerWidth` stayed at the desktop value (~2294), so responsive reflow / header-wrap / no-horizontal-scroll at small widths could not be verified. (At desktop width, `scrollWidth <= innerWidth`, i.e. no horizontal overflow.)
- **Sealed-tome end-to-end (the area the current build's PBKDF2 fix touches).** The full flow (Library → Share → Seal → a `*-sealed.json` **downloads** → re-import into a fresh profile → unlock-gate wrong/right passphrase → refresh re-locks → no-plaintext check) requires a file **download** + a **file-picker re-import** cycle and, to exercise the iteration-count bound specifically, a hand-crafted malicious sealed blob. File downloads are a restricted action and there is no unattended file-upload path here, so this could not be completed. The seal/share dialog itself was reachable without crashing.
- **Offline / PWA real-network-loss matrix.** Toggling the network offline (to verify `saving`→`offline`→`idle` sync states and the service-worker offline shell) requires DevTools network control that is not drivable from this harness.
- **GitHub OAuth sign-in / sign-out + delete-account round trip.** The profile was already signed in (a Supabase session token was present); a real OAuth sign-out/sign-in round trip and account deletion were not exercised to avoid disturbing the user's actual account.
