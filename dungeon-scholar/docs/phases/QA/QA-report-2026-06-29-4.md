### Supabase auth-token refresh fails repeatedly on load — console error storm
- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** initial home load, signed-in real profile (Supabase token present)

**Description:** On every load the console logs a burst of uncaught `TypeError: Failed to fetch` originating in the bundled Supabase gotrue client (`_refreshAccessToken` / `_callRefreshToken`), repeated with backoff (observed 12:31:55, :56, :57, :59, 12:32:03 — 5+ in the first ~8s). The GitHub-Pages shell itself loaded fine, so the network is up; the Supabase token endpoint is unreachable or the stored refresh token is being rejected. The app stays usable (local-first), but the console is noisy and the failures are unhandled at the surface.

**Reproduction:**
1. Open https://evilpatrick06.github.io/home-lab/#/home while signed in (a `sb-*-auth-token` is in localStorage).
2. Open DevTools console.
3. Observe repeated `TypeError: Failed to fetch` from the Supabase client refresh path.

**Expected behavior:** A failed token refresh while offline/unreachable should be caught and folded into the existing quiet "offline / sync paused" state, not streamed as repeated uncaught `Failed to fetch` errors.

**Hypothesis / root cause:** gotrue-js auto-refresh retries on a timer and rethrows the network error to `console.error` each attempt; the app's Supabase wrapper does not swallow/aggregate these into its sync-status UI. Likely `dungeon-scholar/src/services/` (supabase sync client init / refresh handler). Could also be a paused/unreachable Supabase project for this deployment.

**Environment:** signed-in · cloud-sync on (token present) · Oracle on · Dark · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/services/` (supabase sync client)

**Console output:** `TypeError: Failed to fetch ... at wo._refreshAccessToken ... at wo._callRefreshToken`

## 1. Routing & navigation

### Empty hash `#/` is not canonicalized to `#/home`
- **Category:** UX
- **Severity:** info
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** invalid/edge hash sweep

**Description:** `#/bogus`, `#/tome/`, and `#/tome/%2Fx` all correctly bounce to `#/home`. But a bare `#/` renders home yet leaves the URL as `#/` rather than canonicalizing to `#/home`. Cosmetic URL inconsistency only — content is correct.

**Reproduction:**
1. Set the location hash to `#/`. 2. Home renders, but the address bar stays `#/` (other routes show `#/home`).

**Expected behavior:** For consistency with the bounce behavior of other non-canonical hashes, `#/` could rewrite to `#/home`.

**Hypothesis / root cause:** `parseHash('#/')` returns `{screen:'home'}` (empty raw), so the router renders home but never rewrites the empty hash; the canonicalize-on-bounce path only fires for `screen===null`. See `dungeon-scholar/src/router/useHashRoute.js` `parseHash` (empty-string branch).

**Environment:** Dark · desktop · tome loaded

**Related files:** `dungeon-scholar/src/router/useHashRoute.js`

### Study-mode screens (flashcards, quiz, chat) have no semantic page heading
- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** per-screen heading sweep (all 21 SCREENS rendered non-empty)

**Description:** Most screens expose a screen title in an `<h1>`/`<h2>` (library "The Grand Library", shop "The Marketplace", etc.). flashcards, quiz, and chat render their title as decorative styled text only — `main h1, main h2` returns none on those three. **Expected behavior:** Each study mode should expose its name as a real heading (e.g. an `<h2>`) so the document outline and screen-reader navigation reflect the active mode.

**Hypothesis / root cause:** These mode components title with spans/divs rather than heading elements. Likely `dungeon-scholar/src/features/study/FlashcardsMode.jsx`, `QuizMode.jsx`, `ChatMode.jsx`.

## 7. Settings, themes, accessibility

### Light theme: pervasive low-contrast accent / stat text (incl. app-wide player-stats header)
- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Home → Visual Theme → ☀ Light; oklch-aware contrast sweep composited over the real light backdrop `rgb(250,250,249)`

**Description:** In Light theme many accent-colored texts keep their dark-theme color while their surface is now light parchment, dropping well below WCAG AA. Verified, recomputed ratios (fg → composited bg):
- **Player-stats header band — appears on EVERY screen** (the persistent "EXPERIENCE / VICTORIES / DELVES / DRAGONS / Level N • Total XP" strip): gold `rgb(255,210,48)` on parchment `rgb(250,250,249)` → **~1.39:1** (12px). This is the highest-impact instance because it is on all 21 screens.
- **Library tome tag chips** (`#sociology`, `#race`, …): gold `rgb(252,211,77)` on a light-amber pill `rgb(251,242,205)` → **~1.28:1** (10px).
- **Inventory equipment-slot labels** (`Weapon`, `Head`, `Cloak`, `Pet`): bright gold `oklch(0.879 0.169 91.605)` ≈ `rgb(255,210,48)` on parchment → **~1.38:1** (10px).
- **Shop category labels** (`⚗️ Apothecary` gold `rgb(253,224,71)` → **~1.26:1**; `👑 Wardrobe` lavender → low).
- **Bestiary biome headings** measured 2.0–3.5:1 (several below the 3.0 large-text floor).

(Approximate / already-tracked: the **gold action buttons** — "Inscribe a Tome", "Open Tome", "Continue Studying" — and the **rarity badges** ("★ LEGENDARY ★", "★ ACTIVE") scanned ~1.0–1.4 but use CSS-gradient backgrounds the compositor can't read exactly; the gold-action-button variant is **already in `docs/logs/ISSUES-LOG-DUNGEON-SCHOLAR.md`** (~line 199, "App-wide gold action buttons … flip to light-on-gold"). The gold/colored *text labels* documented above — stat header, tag chips, slot labels, category/biome headings — are an additional, distinct surface beyond buttons.)

**Reproduction:**
1. Home → Visual Theme → ☀ Light. 2. Visit Home/Library/Shop/Inventory/Bestiary. 3. The gold/colored labels and the player-stat header strip are washed out on the light surfaces.

**Expected behavior:** Accent text on a surface that lightens in Light theme must darken too (inverting `var(--color-amber-*)` / theme token), per `DESIGN-CONSTRAINTS.md` §"Light-theme surfaces must route through theme vars (Phase 03)" — "the *text* must darken too."

**Hypothesis / root cause:** These labels use fixed Tailwind/oklch accent colors (`text-amber-300/400`, etc.) that don't invert with `html[data-theme="light"]`. Phase 03 fixed the *dark-on-dark background* class but the *light-on-light accent-text* class remains on these surfaces.

**Environment:** Light theme · desktop · tome loaded — Dark (default) unaffected

**Related files:** player-stats header component; `dungeon-scholar/src/features/library/LibraryScreen.jsx`, `.../shop/*`, `.../inventory/*`, `.../progression/BestiaryScreen.jsx`; `dungeon-scholar/src/index.css` (light-theme vars)

### Light theme: "Begin Anew" reset button is dark-on-dark (hardcoded dark `rgba()` background)
- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Light theme, contrast verification of the Home reset control

**Description:** In Light theme the **Begin Anew** reset-progress button keeps `background-color: rgba(41,12,12,0.7)` (which composites to ~`rgb(104,83,83)` dark brown over the light page) with `color: oklch(0.505 0.213 27.518)` ≈ `rgb(193,0,7)` (deep red). Composited contrast ≈ **1.1:1** — the label is nearly invisible while everything around it is light. Exactly the failure `DESIGN-CONSTRAINTS.md` §Phase-03 warns against: a hardcoded dark `rgba(...)` background under inverting `text-*` utilities → dark-on-dark in light theme.

**Reproduction:**
1. Home → Visual Theme → ☀ Light. 2. Scroll to "Begin Anew". 3. The button is dark with barely-legible red text against the light page.

**Expected behavior:** Route the button background through the theme vars (`--panel-bg-*` / a danger token) so it lightens in Light theme and the label keeps AA contrast.

**Hypothesis / root cause:** A remaining instance of the Phase-03 dark-on-dark pattern — the reset/danger button hardcodes `rgba(41,12,12,0.7)` instead of an inverting var (search `rgba(41, 12, 12` or the "Begin Anew" label).

**Environment:** Light theme · desktop · tome loaded — Dark unaffected

**Related files:** `dungeon-scholar/src/` (Home/reset button styling); cf. `dungeon-scholar/docs/DESIGN-CONSTRAINTS.md` §Phase-03
