## 2. Library & tomes

### Sealed-tome export path skips `stripLocalOnlyTomeFields` — inconsistent with the plain-export path

- **Category:** security
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** static review of the phase-11 local-notes strip against all export call sites

**Description:** The resolver round added `stripLocalOnlyTomeFields` to `encodeTomeShareCode`, `normalizeTomeData` (import), and `downloadTomeJson` (plain `.json` export). The **seal** path does not get the same guard: `ShareTomeModal.jsx:67` calls `sealTome(tome.data, sealPass)` on the raw `tome.data`, then wraps the envelope in `downloadTomeJson({ data: envelope })` — the strip at that point runs on the envelope (which has no `notes` key), not on the payload that was just encrypted. Normally `tome.data.notes` never exists (Phase-40F notes are a sibling of `data`), but the strip was added precisely because "an attacker-injected `data.notes` can ride in through import" (`tome.js` comment): any tome imported **before** the strip landed can still carry an injected `data.notes` in the library, and the sealed-export path is now the one remaining exit that forwards it.

**Reproduction (static; not browser-verified):**
1. A library entry whose `tome.data.notes` was injected via import prior to `15f27e5a`.
2. Library → Share → Seal for proctored use.
3. `sealTome` encrypts `data` including `notes`; the `-sealed.json` carries it to anyone who unseals.

**Expected behavior:** All four data exits (share code, import normalize, plain export, seal) apply the same local-only-field strip.

**Hypothesis / root cause:** `ShareTomeModal.jsx:67` — `sealTome(tome.data, sealPass)` predates the strip helper and was not included in the phase-11 call-site sweep.

**Suggested action:** `sealTome(stripLocalOnlyTomeFields(tome.data), sealPass)` (one-line change), plus a guard test alongside `tome.test.js`.

**Environment:** static source review @ `0b17da31` — **unverified — no browser this run.**

**Related files:** `dungeon-scholar/src/features/library/ShareTomeModal.jsx:67`, `dungeon-scholar/src/game/tome.js`

## 3. Study modes

### OcclusionCard disallowed-image fallback never reveals mask answers on flip but still asks the user to self-grade

- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** static review of the resolver-round OcclusionCard allowlist hardening

**Description:** `OcclusionCard.jsx` now (correctly) refuses to render a non-`data:image` occlusion image and shows "Image unavailable — occlusion images must be embedded (data:image) images." But the mask layer is gated on the same `imageOk` flag, so on flip the region **answers** (`m.answer`) are never shown either — while the footer hint still reads "~ Name each masked region, then flip ~" / "✦ Revealed — rate thy recall", and FlashcardsMode still presents the SRS rating buttons. The learner is asked to rate recall of answers the card never revealed, which will silently skew SRS scheduling for that card.

**Expected behavior:** When the image is rejected, flipping should still list the mask answers as plain text (they are text data, independent of the image), or the card should be excluded from rating with a clearer message.

**Hypothesis / root cause:** `imageOk && masks.map(...)` gates the whole mask layer, including its flipped answer-text role — the allowlist fix conflated "can’t position masks over an image" with "can’t show answers at all."

**Suggested action:** In the `!imageOk` branch render a simple flipped-state answer list (`masks.map(m => m.answer)`), and make the footer hint conditional on `imageOk`.

**Environment:** static source review @ `0b17da31` — **unverified — no browser this run** (also requires crafting a tome with a non-data: occlusion image).

**Related files:** `dungeon-scholar/src/components/OcclusionCard.jsx`, `dungeon-scholar/src/features/study/FlashcardsMode.jsx`
