Remaining nit: a burst of uncaught errors still reaches the console on every load before the ceiling trips (a backoff sequence of ~8 spaced attempts plus a cluster of stacked failures at the ceiling moment), because the gotrue client logs each internal retry. Bounded and self-terminating, but visibly noisy on each fresh load.

**Reproduction:**
1. Open https://evilpatrick06.github.io/home-lab/#/home signed in (an `sb-*-auth-token` is in localStorage).
2. Watch the console for ~30s.

Could be further muffled by gating the probe behind a single reachability check or downgrading the client's console verbosity.

**Suggested action:** Consider a one-shot reachability HEAD probe before arming the refresh ticker, or wrap/suppress the gotrue retry logging; or surface one friendly "cloud sync offline" line instead. The functional behavior (local-first, breaker stops the loop) is already correct — this is console-noise polish.

## 1. Routing & navigation

### Bad-id deep link to a gated screen does not reset to home on fresh load — PHASE-08 08A reset defeated by a replaceState/screenRef race
- **Category:** bug
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** routing — deep-link handling, `#/tome/<bad-id>/<gated-screen>`

**Description:** Opening `#/tome/does-not-exist-123/dungeon` as a **fresh page load** rests on `#/dungeon` with the Dungeon UI rendered (against the existing active tome) and shows **no** "That tome is not in thy library" toast. PHASE-08 08A (`App.jsx:733-738`) intends to `setScreen('home')` + notify when the deep-link tome id does not resolve, so a gated screen is not rendered against a stale tome. On the **in-page** hashchange path the toast does fire, but the screen still does not reliably settle on home. So 08A's protective reset is not effective on its exact target scenario (a deep link opened cold).

**Reproduction:**
1. In a tab already on the app, set the URL to `https://evilpatrick06.github.io/home-lab/#/tome/does-not-exist-123/dungeon` and hard-reload (or open it fresh).
2. Wait for load.
3. Observed: URL canonicalizes to `#/dungeon`, the Dungeon screen renders, no error toast. Expected (per 08A): reset to `#/home` with a "not in thy library" notice.

**Expected behavior:** An unresolvable deep-link tome id lands on home with the "That tome is not in thy library" toast, regardless of load vs in-page navigation.

**Hypothesis / root cause:** In the `pendingTomeId` effect (`App.jsx:723-743`), the not-found branch calls `setScreen('home')` (which sets `location.hash='#/home'` and queues a hashchange) and then immediately `clearPendingTome()`, which does `history.replaceState(null,'',formatHash(screenRef.current))`. `screenRef.current` is still the stale `'dungeon'` (the ref is updated in a separate post-render effect), so replaceState rewrites the URL back to `#/dungeon` before the queued hashchange runs; the hashchange handler then reads the now-`#/dungeon` location and re-sets the screen to dungeon — undoing 08A's home reset. See `useHashRoute.js` `clearPendingTome` + the `onHashChange` handler.

**Suggested action:** Have `clearPendingTome` accept/replace with the intended target screen (e.g. pass `'home'`) rather than reading the stale `screenRef`, or sequence the reset so the canonicalizing replaceState uses the post-reset screen. Verify the null-active-tome path too (below).

**Practical impact:** Low — with a valid active tome loaded, the gated screen renders correctly against that tome, so there is no broken/blank state; the downstream courseSet-gated guard (`App.jsx` ~line 745+) still covers the genuinely dangerous null-tome case. The visible deviation is the URL/screen not matching 08A's documented reset and the missing toast on cold load.

**Environment:** signed-in (real profile) · valid active tome loaded · Dark · desktop

**Related files:** `dungeon-scholar/src/App.jsx` (723-743), `dungeon-scholar/src/router/useHashRoute.js` (clearPendingTome / onHashChange)

**Could not fully verify:** the null-active-tome branch (08A's worst case) needs the active tome unloaded, which would mutate the real profile's state, so it was not forced this run — see Could not test.


## 7. Settings, themes, accessibility

### Light theme: accent / tag / stat text stays light-gold while panels lighten — ~1.23:1 (illegible) on the active-tome tag pills
- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** theme matrix — Dark vs Light, home screen active-tome panel

**Description:** In Light theme the gold accent text (tag pills like `#sociology`, the XP `162 / 1118` strip, the `98` victories stat, the tome title) keeps its dark-theme light-gold colour (`rgb(252,211,77)` / `oklab(L 0.68)`) while the panel background lightens to parchment. Measured gradient-aware (oklab to sRGB, compositing over the panel's actual lightened gradient, not the page bg): the `#sociology` tag pill is **8.22:1 in Dark** but **1.23:1 in Light** — well below the 4.5:1 AA text threshold and effectively illegible (gold on cream). The same pattern affects the tome title (~1.19:1) and the muted description line (~1.07:1) on the home active-tome panel.

**Reproduction:**
1. Home, then Visual Theme, then Light.
2. Look at the Active Tome panel's hashtag pills, title, and the level/XP strip.
3. Observed: light-gold text on a light parchment panel; the pills are barely distinguishable from the background.

**Expected behavior:** Accent/stat/tag text on theme-aware (lightening) panels must darken in Light theme to keep at least 4.5:1 (3:1 for large text), per DESIGN-CONSTRAINTS.md (when the background is theme-aware the text must darken too — use an inverting amber utility, not a fixed light hex).

**Hypothesis / root cause:** The tag pills / stat numbers use a fixed light-gold colour (a literal `rgb(252,211,77)` / non-inverting token) rather than an inverting `text-amber-*` / `var(--color-amber-*)` utility, so they do not flip to dark ink when `html[data-theme="light"]` inverts the ramps — while the surrounding `--panel-bg-*` gradient does lighten. Same class as DESIGN-CONSTRAINTS.md's Phase-03 note; these particular surfaces (home tag pills / XP strip / victories stat / tome title) were not converted.

**Suggested action:** Route the tag-pill / stat / tome-title text through an inverting amber utility or an `--accent-ink` var that darkens under `[data-theme="light"]`.

**Environment:** signed-in (real profile) · Dark/Light via data-theme (CSS-only toggle, no profile write) · desktop · active non-sealed tome

**Related files:** `dungeon-scholar/src/index.css` (light-theme ramp inversion), home active-tome panel + tag-pill components under `dungeon-scholar/src/features/` / `components/`, `OrnatePanel.jsx`

**Note:** Carries forward the Light-theme low-contrast accent/stat class from `QA-report-2026-06-29-4.md` (logged Medium there); re-confirmed present on the newer build `index-Dw_qfUwQ.js` with a clean gradient-aware ratio (1.23:1 on the tag pills).
