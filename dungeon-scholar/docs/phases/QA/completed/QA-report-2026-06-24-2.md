### Stale service-worker precache crashes EVERY in-app navigation for returning users after a deploy (High)
- **Category:** bug · **Severity:** high · **Domain:** dungeon-scholar · **Discovered by:** QA Agent
- **During:** Phase 1 — navigating from `#/home` to any other screen on a profile that had the app cached before the latest deploy
**Description:** On a returning visit (service worker + Workbox precache already installed from a previous build `index-DSXcG4P0.js`), `#/home` loads fine but navigating to **any** lazy-loaded route — library, shop, inventory, crafting, bestiary, stable, spellbook, calendar, ascension, history, quests, domainStudy, vault, dungeon, flashcards, quiz, lab, chat, practiceExam, ledger (all 20) — immediately drops into the "⚠ SOMETHING WENT WRONG ⚠ / A spell misfired in this chamber" error boundary. The page body collapses to the boundary view. The deployed app shell advanced (new chunk hashes) but the precached old `index` still requests the **old** chunk filenames, which now 404.
**Reproduction:**
1. Load the app once on an older build so the SW precaches it.
2. Deploy advances (new hashed chunks ship); revisit `#/home` — loads.
3. Click any nav target (e.g. Library). → error boundary; console: `TypeError: Failed to fetch dynamically imported module: https://…/assets/LibraryScreen-Cu731Kh-.js` then `[Dungeon Scholar] ErrorBoundary caught: Failed to fetch dynamically imported module…`.
4. After unregistering the SW + clearing caches + a fresh document load (new shell `index-B4qcBDzT.js`), all 20 routes render cleanly — confirming the crash is purely stale-precache, not a per-route defect.
**Expected:** A new deploy should not hard-crash returning users on every navigation. On a failed dynamic import the app should detect the stale shell and self-heal (skipWaiting + clients.claim + one automatic reload, or catch the chunk-load error and force an update) rather than dead-ending at the error boundary.
**Hypothesis / root cause:** Workbox precache serves the previous `index` whose code-split chunk URLs are immutable-hash names that no longer exist after the deploy; the SW update/`skipWaiting` flow does not activate + reload promptly, and the lazy-import error path has no chunk-load-failure recovery. The "service-worker update resilience" work (commit 530aa8dd) does not auto-recover from this failure mode.
**Suggested action:** Add a dynamic-import error handler that, on "Failed to fetch dynamically imported module", triggers `registration.update()` / `skipWaiting` and a single auto-reload; ensure the SW takes control and purges the old precache on activate. Consider `navigateFallback` revalidation so the freshest `index` wins.
**Related files:** `dungeon-scholar/src/` SW registration + `ErrorBoundary`, `vite.config.js` (Workbox config), router lazy imports.
**Console output:** `Failed to fetch dynamically imported module: …/assets/LibraryScreen-Cu731Kh-.js`
**Note:** previously reported in `completed/QA-report-2026-06-24.md` (dd0b1d97) as High — **re-confirmed still present on the current build**; the deploy that shipped since then re-triggered it for any already-cached user.

### Light theme: flashcard question AND answer are unreadable (dark-on-dark, ~1.04:1 contrast)
- **Category:** bug · **Severity:** high · **Domain:** dungeon-scholar · **Discovered by:** QA Agent
- **During:** Phase 3 — Flashcards mode, light theme (the active profile's saved theme)
**Description:** In light theme the flashcard face text (both the "✦ THE QUESTION ✦" body and, after flipping, the "✦ THE ANSWER ✦" body) renders dark brown on the card's fixed dark-navy gradient. Measured contrast ratio ≈ **1.04:1** (WCAG AA needs 4.5:1) — the question/answer are effectively invisible; you cannot study without flipping to dark theme.
**Reproduction:**
1. Ensure theme = Light (Home → Visual Theme → ☀). 2. Load a tome, open Flashcards. 3. The question text is invisible; tap to reveal — the answer is equally invisible.
**Measured:** card bg `linear-gradient(135deg, rgba(12,24,41,.85), rgba(6,12,20,.95))` ≈ rgb(26,36,54); face text computed `oklch(0.279 0.077 45.635)` ≈ rgb(70,25,1); contrast 1.04:1.
**Hypothesis / root cause:** Light theme **inverts the Tailwind amber ramp** via CSS custom properties — with `data-theme="light"`, `--color-amber-50` resolves to `oklch(27.9% .077 45.635)` (dark) and `--color-amber-950` to `oklch(98.7% .022 95.277)` (light). This makes ordinary parchment screens readable (dark ink on light bg), but `FlashcardsMode.jsx` gives the card a **hardcoded dark gradient** (`src/features/study/FlashcardsMode.jsx:341`) while the face text relies on the inherited/`text-amber-50` color (`:353`), which is now dark → dark-on-dark. The app-root `min-h-screen text-amber-50` inherits the same now-dark color, so any other component with a hardcoded dark surface in light theme will have the same problem.
**Suggested action:** For components that hardcode a dark background regardless of theme (flashcard card, any dark panels/overlays), pin the face text to a theme-independent light token (e.g. a fixed `#fff7ed`/raw light value, not `amber-50`), or give the card a theme-aware background so it isn't dark in light theme. Audit all `text-amber-50/100/200` usages that sit on hardcoded dark surfaces.
**Related files:** `dungeon-scholar/src/features/study/FlashcardsMode.jsx:339-356`; the light-theme amber-ramp inversion in the global CSS/theme tokens.
**Note:** functionally the mode works — flip + FSRS self-grade (Again/Hard/Good/Easy) advance correctly (graded "Good" → Scroll 1→2 of 3, flips back to question). This is purely a light-theme contrast defect.
