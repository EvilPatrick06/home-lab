### Supabase token-refresh spams the console with a repeating `Failed to fetch` / `AuthRetryableFetchError` storm (re-confirmed on new build `index-CkFA4t7H.js`)

- **Category:** bug
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** setup — first load of `#/home` with a signed-in (cloud-sync) session

**Description:** On a signed-in load, the console accumulates uncaught `TypeError: Failed to fetch` errors originating from the Supabase auth client's token-refresh path (`wo._refreshAccessToken` -> `wo._callRefreshToken`), plus `AuthRetryableFetchError: Failed to fetch` from the retry wrapper. They are logged as uncaught ERRORs (red), not handled warnings. The retry cadence does back off (observed firing at +1s, +1s, +1s, +2s, +4s, +7s, +13s — exponential), so it is not an unbounded-rate storm, but every attempt still surfaces as an uncaught console error with no logging ceiling/de-dupe. UI stays fully usable. The Supabase auth host (`wivnzcbufpqdjwycampb.supabase.co`) is unreachable from this network and/or the stored refresh token is stale — the degraded path that should be handled quietly. Already tracked: "Supabase token-refresh console noise" -> bundled into **PHASE-02**; re-confirmed present on the new build.

**Reproduction:**
1. Sign in (cloud sync active; `sb-…-auth-token` present in localStorage).
2. Load `https://evilpatrick06.github.io/home-lab/#/home` with the DevTools console open.
3. Observe repeating `_refreshAccessToken`/`_callRefreshToken` + `AuthRetryableFetchError` errors on a backing-off interval.

**Expected behavior:** A failed token refresh (offline / unreachable Supabase / stale token) should be caught and surfaced once as a single handled warning, reflected in the sync-status UI (`offline`) — not logged as a stream of uncaught errors.

**Hypothesis / root cause:** `gotrue-js`'s background auto-refresh timer fires while the auth endpoint is unreachable; the rejection isn't caught before reaching `console.error`, and there is no de-dupe/ceiling on logging. `already in PHASE-02` — root cause unchanged.

**Suggested action:** Catch the refresh rejection in the Supabase sync service, map it to the existing `offline`/`idle` sync-status surface, and de-dupe/throttle the logging.

## 1 Routing and navigation

### Deep link `#/tome/<bad-id>/<screen>` lands on the (gated) screen against the previously-active tome instead of bouncing home (re-confirmed)

- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** routing — `#/tome/<id>` vs `#/tome/<id>/<screen>` with a bogus tome id

**Description:** `#/tome/nonexistent-xyz` correctly resolves to `#/home`. But `#/tome/nonexistent-xyz/quiz` resolves to `#/quiz` and stays there: because the bogus tome can't load, the *previously active* tome remains loaded, so the gated `quiz` screen passes its course-set gate and renders against the wrong tome. The two forms of the same not-found condition diverge (one bounces home, one honors the screen segment). Re-confirmed on build `index-CkFA4t7H.js`; matches the prior 2026-06-29 report.

**Reproduction:**
1. With an active tome loaded, set hash to `#/tome/<id-that-does-not-exist>/quiz`.
2. URL canonicalizes to `#/quiz` and the quiz renders (against the still-active prior tome) rather than bouncing to `#/home` the way `#/tome/<bad-id>` (no screen) does.

**Expected behavior:** `#/tome/<id>/<screen>` whose `<id>` doesn't resolve should behave like `#/tome/<id>` with no screen — bounce to `#/home` (optionally with a "tome not found" toast).

**Hypothesis / root cause:** In `useHashRoute.js` the `#/tome/<id>/<screen>` branch sets the screen from the segment and attempts the load, but a failed/no-op load doesn't reset the screen back to home — whereas screen-less `#/tome/<id>` defaults to home. The two branches handle load-failure inconsistently. `already in prior QA report (2026-06-29)`.

**Suggested action:** Gate the screen segment on a successful tome resolution; on load failure fall through to the same home-redirect the screen-less branch uses.

**Environment:** signed-in · cloud-sync on · Dark theme · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/router/useHashRoute.js`, `dungeon-scholar/src/router/screens.js`, `dungeon-scholar/src/App.jsx`

### Light theme: flashcard card keeps a hardcoded DARK navy gradient → dark question text is dark-on-dark (re-confirmed on new build; PHASE-03)

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** themes — Home -> Visual Theme -> Light, then Flashcards

**Description:** In Light theme the flashcard foreground ink switches to the dark Light-theme ink (question body computes to `oklch(0.279 0.077 45.635)`, a dark brown), but the card panel **background does not switch** — it stays a hardcoded dark navy gradient `linear-gradient(135deg, rgba(12,24,41,…) …)`. Result: dark text on a dark card. Measured live: question "What is the one-drop rule…" -> contrast **2.02**; the "THE QUESTION" header (blue `oklch(0.588 …)`) on that gradient -> **1.09**; the "Touch the scroll to reveal" hint -> **1.81** — all below WCAG AA (4.5). Re-confirmed unchanged on build `index-CkFA4t7H.js`. Tracked as **PHASE-03 F1 / 03B (pending)**.

**Reproduction:**
1. Home -> Visual Theme -> Light.
2. With a tome loaded, open Flashcards.
3. Observe dark question text on the dark navy card gradient.

**Expected behavior:** In Light theme the card panel should use a light/parchment gradient (or invert the text) so card text meets AA contrast in both themes.

**Hypothesis / root cause:** The card's `background-image` gradient is a theme-agnostic literal, not driven by a `data-theme`-scoped CSS variable, so only the foreground ink responds to Light theme. Because it is a `background-image` (not `background-color`), a theme override that only sets `background-color` won't cover it. `already in PHASE-03 (pending)`.

**Suggested action:** Drive the card gradient from `data-theme`-scoped CSS variables (parchment gradient for `[data-theme=light]`); verify with a contrast check.

**Environment:** signed-in · cloud-sync on · **Light** theme · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/features/flashcards/` (card panel) + theme tokens in `dungeon-scholar/src/styles/`

### Inconsistent date formatting across screens: Shop uses ISO (`2026-06-29`), Practice-Exam history uses US `M/D/YYYY` (`6/28/2026`)

- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** copy/consistency — comparing date renderings across screens

**Description:** The Shop header stamps the rotating-stock date in ISO format ("ROTATING WARES — **2026-06-29**"), while the Practice-Exam attempt-history entry renders the same kind of date in US locale format ("**6/28/2026** · 30 riddles · 2m 2s — abandoned"). Within one app, two different date formats for user-facing dates is an inconsistency (and the locale-dependent `M/D/YYYY` is ambiguous internationally). Not found in the issues/suggestions logs or prior QA reports — appears to be a new (un-tracked) observation.

**Reproduction:**
1. Open `#/shop` — note the ISO date in the header.
2. Open `#/practiceExam` — note the prior-attempt date in `M/D/YYYY`.

**Expected behavior:** Pick one user-facing date format (ISO `YYYY-MM-DD` is the more locale-safe choice given the app already uses it in Shop) and apply it consistently across Shop, Practice-Exam history, Chronicle/history, etc.

**Hypothesis / root cause:** Shop formats with a fixed ISO string while the exam-history entry uses `Date.prototype.toLocaleDateString()` (or `.toLocaleString()`) without a fixed locale/format, so it renders in the runtime locale's short format.

**Suggested action:** Centralize date formatting in one helper and use it everywhere user-facing dates appear.

**Environment:** signed-in · cloud-sync on · Dark theme · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/features/study/ExamMode.jsx` (history entry), the Shop screen component, and any shared date util in `dungeon-scholar/src/services/` or `.../utils/`.
