### Supabase token-refresh spams the console with a repeating `Failed to fetch` / `AuthRetryableFetchError` storm (re-confirmed on new build)

- **Category:** bug
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** setup — first load of `#/home` with a signed-in (cloud-sync) session

**Description:** Within ~90s of load the console accumulated **90+** identical errors — `TypeError: Failed to fetch` and `AuthRetryableFetchError: Failed to fetch` — all originating from the Supabase auth client's token-refresh path (`wo._refreshAccessToken` → `wo._callRefreshToken`, plus the `AuthRetryableFetchError` retry wrapper). They are logged as uncaught ERRORs (not handled/warned) and fire in retry bursts (a handful on first load, then a storm of ~30 at once). The UI stays fully usable, but a signed-in user with DevTools open sees a continuously growing wall of red. Same "Supabase token-refresh console noise" already tracked (prior QA report 2026-06-28 → bundled into `PHASE-02`); re-confirmed present and, if anything, noisier (retry storm to 90+) on build `index-C2MmghGQ.js`. The Supabase auth host (`wivnzcbufpqdjwycampb.supabase.co`) appears unreachable from this network / the stored refresh token is stale, which is exactly the degraded path that should be handled quietly.

**Reproduction:**
1. Sign in (cloud sync active; `sb-…-auth-token` present in localStorage).
2. Load `https://evilpatrick06.github.io/home-lab/#/home` with the DevTools console open.
3. Observe 7+ errors on load, escalating to 90+ within ~90s, all from `_refreshAccessToken`/`_callRefreshToken` + `AuthRetryableFetchError`.

**Expected behavior:** A failed token refresh (offline / unreachable Supabase / stale refresh token) should be caught and surfaced once as a single handled warning and reflected in the sync-status UI (`offline`), not logged as an unbounded stream of uncaught errors with no backoff ceiling.

**Hypothesis / root cause:** `gotrue-js`'s background auto-refresh timer fires repeatedly while the Supabase auth endpoint is unreachable; the rejection isn't caught before reaching `console.error`, and the retry cadence has no de-dupe/ceiling on logging. Wrap the refresh call in the sync service and map failures to the existing `offline`/`idle` status. `already in PHASE-02` — root cause unchanged.

**Suggested action:** Catch the refresh rejection in the Supabase sync service, map it to the `offline` sync-status surface, and de-dupe/throttle the retry logging.

**Environment:** signed-in · cloud-sync on · Dark theme · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/services/` (supabase sync/auth client wiring)

**Console output:** `TypeError: Failed to fetch … at wo._refreshAccessToken (…:25:19529) at wo._callRefreshToken (…:25:22519)` and `AuthRetryableFetchError: Failed to fetch (…:24:16696)` — 90+ occurrences in ~90s.

## 1 Routing & navigation

### Deep link to a nonexistent tome WITH a trailing screen lands on that (gated) screen instead of bouncing home

- **Category:** UX
- **Severity:** low
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** routing — `#/tome/<id>` vs `#/tome/<id>/<screen>` with a bogus tome id

**Description:** `#/tome/nonexistent-id-xyz` correctly resolves to `#/home` (tome not found → home). But `#/tome/nonexistent-id-xyz/quiz` resolves to `#/quiz` and stays there. Because the bogus tome can't load, the *previously active* tome remains loaded, so the gated `quiz` screen passes its course-set gate and renders against the wrong tome — a user following a stale/typo'd share link to a specific screen silently studies their old tome rather than being told the link's tome doesn't exist. The two forms of the same not-found condition diverge (one bounces home, one honors the screen segment).

**Reproduction:**
1. With an active tome loaded, set hash to `#/tome/<id-that-does-not-exist>/quiz`.
2. Observe URL canonicalizes to `#/quiz` and the quiz screen renders (against the still-active prior tome), rather than bouncing to `#/home` the way `#/tome/<bad-id>` (no screen) does.

**Expected behavior:** A `#/tome/<id>/<screen>` whose `<id>` doesn't resolve should behave the same as `#/tome/<id>` with no screen — bounce to `#/home` (optionally with a "tome not found" toast).

**Hypothesis / root cause:** In `useHashRoute.js` the `#/tome/<id>/<screen>` branch sets the screen from the segment and attempts the tome load, but a failed/no-op load doesn't reset the screen back to home — whereas the screen-less `#/tome/<id>` branch defaults to home. The two branches handle the load-failure case inconsistently.

**Suggested action:** Gate the screen segment on a successful tome resolution; on load failure fall through to the same home-redirect the screen-less branch uses.

**Environment:** signed-in · cloud-sync on · Dark theme · desktop · active tome loaded

**Related files:** `dungeon-scholar/src/router/useHashRoute.js`, `dungeon-scholar/src/router/screens.js`, `dungeon-scholar/src/App.jsx`

## 3 Study modes

### Light theme: flashcard card keeps a hardcoded DARK gradient background → dark question text is dark-on-dark (re-confirmed; root cause located)

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** themes — switching Home → Visual Theme → ☀ Light, then viewing flashcards

**Description:** In Light theme the flashcard text colors switch to the Light-theme dark "ink" (question label/body computed to `oklch(0.279 …)`, a dark brown), but the card's **background does not switch** — it stays a hardcoded dark navy gradient `linear-gradient(135deg, rgba(12,24,41,0.85) 0%, rgba(6,…) …)` applied as a `background-image` on the card panel (`div.rounded-sm.p-8.min-h-[300px]`). Result: **dark text on a dark card** in Light mode — the front question and the reveal hint are hard to read. Same Light-theme flashcard contrast regression noted in the 2026-06-28 report; it is captured in **`PHASE-03-light-theme-dark-on-dark-contrast.md` (status: pending)** in the phase index. Re-confirmed present and unchanged on the current build, with the specific offending rule now located.

**Reproduction:**
1. Home → Visual Theme → ☀ Light.
2. Load a tome, open Flashcards.
3. Observe the question text is dark and the card panel behind it is a dark navy gradient → low contrast.

**Expected behavior:** In Light theme the card panel background should use a light/parchment surface (or the text should invert), so card text meets WCAG AA contrast in both themes.

**Hypothesis / root cause:** The card panel's `background-image: linear-gradient(135deg, rgba(12,24,41,.85)…)` is a theme-agnostic literal (not driven by a CSS custom property that flips per `data-theme`), so only the foreground ink responds to Light theme. Because it's a `background-image` (not `background-color`), a theme override that only sets `background-color` won't cover it.

**Suggested action:** Drive the card gradient from `data-theme`-scoped CSS variables (a light parchment gradient for `[data-theme=light]`); verify with a contrast check.

**Environment:** signed-in · cloud-sync on · **Light** theme · desktop · active tome loaded · `already in prior QA report / PHASE-03 (pending)`

**Related files:** `dungeon-scholar/src/features/flashcards/` (card panel component + its theme CSS), `dungeon-scholar/src/styles/` (theme tokens)
