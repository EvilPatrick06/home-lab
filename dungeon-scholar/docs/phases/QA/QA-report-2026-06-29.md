### Light theme: the entire Chat/Oracle conversation (user messages AND Oracle answers) is pale-cream-on-near-white — effectively invisible

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** Chat (Oracle), Light-theme contrast check

**Description:** In Light theme, both the user's sent message and the Oracle's reply render in pale amber/cream text on a near-white parchment background at WCAG ratios ~**1.0–1.4** (illegible). Measured live: Oracle answer body `rgb(254,243,199)` on `rgba(254,243,198,.7)` → **~1.0**; user message `rgb(254,243,199)` on `rgb(250,250,249)` → **1.07**; "🪄 THE ORACLE" label gold `rgb(252,211,77)` → **1.29**. This makes Chat unusable in Light theme. Extends the 06-28 "Oracle answer text is light-on-light" item — **still unresolved on build index-C2MmghGQ.js**, and broader (the user-message bubble is affected too).

**Reproduction:**
1. Home → Visual Theme → ☀ Light. 2. Load a tome, open Chat, ask any question. 3. Both the question and the Oracle answer are near-invisible pale text on cream.

**Expected behavior:** Chat bubbles use a light-theme dark text color + contrasting bubble bg meeting WCAG AA (≥4.5:1).

**Hypothesis / root cause:** Chat text uses a hard-coded dark-theme token (amber-100 `#fef3c7` = `rgb(254,243,199)`) with no `[data-theme="light"]` override, so light text lands on the light parchment surface.

**Suggested action:** Add light-theme overrides for chat message text + bubble background; add a contrast assertion to the light-theme check.

**Environment:** signed-out/local · Oracle reachable · **Light** · desktop · throwaway tome

### Supabase auth token-refresh fails in a perpetual retry loop, spamming the console (backend host unreachable)

- **Category:** bug
- **Severity:** medium
- **Domain:** dungeon-scholar
- **Discovered by:** QA Agent
- **During:** console review across screens; §6 cloud-sync matrix

**Description:** The console fills with recurring `TypeError: Failed to fetch` from the Supabase auth client (`wo._refreshAccessToken` → `_callRefreshToken`) and `AuthRetryableFetchError: Failed to fetch` (~164 messages over ~12 min, retrying on backoff). Root cause: the Supabase host `wivnzcbufpqdjwycampb.supabase.co` is **unreachable** — bare `fetch('https://wivnzcbufpqdjwycampb.supabase.co/')` and `/auth/v1/health` both reject with `TypeError: Failed to fetch` (network-level, not CORS) — the project appears paused/down/unresolvable. The **UI degrades correctly** (shows "Sign in with GitHub to sync", runs on localStorage), but the gotrue client keeps a stale token and retries refresh indefinitely in the background, generating continuous console errors. Same symptom as `QA-report-2026-06-28.md` — **recurring/unresolved on build index-C2MmghGQ.js**, now with confirmed root cause (host unreachable).

**Reproduction:**
1. Load the live app with a stale Supabase token in `localStorage`. 2. Console → recurring `Failed to fetch` / `AuthRetryableFetchError`. 3. `fetch('https://wivnzcbufpqdjwycampb.supabase.co/')` → `TypeError: Failed to fetch`.

**Expected behavior:** Cap/circuit-break refresh retries on repeated network failure; clear or quarantine the unusable token so the client stops hammering. (User-facing state is already correct.)

**Hypothesis / root cause:** Deployment's Supabase project is down/paused; the gotrue auto-refresh retries with no app-level circuit breaker. Separately, confirm whether the Supabase project should be live for this deployment.

**Suggested action:** Add a refresh-failure circuit breaker; drop the stale token when the backend is unreachable. Verify the Supabase project status.

**Environment:** signed-out/local UI (stale token present) · backend unreachable · Dark · desktop

**Console output:** `TypeError: Failed to fetch` at `wo._refreshAccessToken`/`_callRefreshToken`; `AuthRetryableFetchError: Failed to fetch` (repeating with backoff).
